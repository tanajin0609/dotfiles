# decisions.md 書き方規約

対象: dev系サブプロジェクトの `docs/changes/<change>/decisions.md`。
書き手（人・AI）とレビュー側（Checker・/archive）が同じ基準を参照し、指摘は規約IDで行う（例: 「D-03違反」）。
MUST は必ず満たす。SHOULD は原則満たし、外す場合は理由を書く。

## A. 単体で読める

| ID | 強度 | 規約 |
|---|---|---|
| D-01 | MUST | 詳細節の「背景」には、この変更で実際に起きている問題と「なぜ今決めるか」を書く。仮定形の一般論で済ませない |
| D-02 | SHOULD | decisions.md だけで判断が読めるようにする。proposal.md への参照だけで背景を済ませない |

NG: 「同じ保管先に置くと漏洩リスクが高まる」 / OK: 「現在 A と B が同じフォルダに出力され、権限を分けられない」

## B. 事実と根拠

| ID | 強度 | 規約 |
|---|---|---|
| D-03 | MUST | 前提事実はコード・仕様・APIレスポンスなど第三者が確認できる一次資料と照合し、出典と確認日を書く |
| D-04 | MUST | 「ユーザー選択」「打ち合わせで確認」だけを根拠にしない。誰が決めたかは承認状況に書き、根拠欄には事実の出典を書く。未検証の事実は「決定しないこと」に回す |
| D-05 | MUST | 参照は行番号で指さない。他changeの決定は `<version> の Qn（論点名）` で指す |

## C. 書くこと・書かないこと

| ID | 強度 | 規約 |
|---|---|---|
| D-06 | MUST | 進捗・タスク・担当・工程表を書かない（checklist.md / backlog.md へ）。移行中の要件は制約として書く |
| D-07 | SHOULD | 粒度の判定: 「採用した方式を別の方式に置き換えたとき、この記述を書き換える必要があるか」。必要なら関数名・環境変数名・アルゴリズムなどの記述は components.md・spec へ移す |
| D-08 | SHOULD | 今回決めないことは「決定しないこと」に書き、委譲先を実在する文書パスか後続changeで名指しする |
| D-09 | SHOULD | 「結果」には採用で受け入れるトレードオフを書く。利点だけを並べない |

NG（D-06）: `- [ ] 来週本番に反映` / OK: 「移行期間中は旧形式と新形式の両方を読めること」

## D. 決定同士の整合

| ID | 強度 | 規約 |
|---|---|---|
| D-10 | MUST | 過去の決定を覆す場合は「置換」に旧決定を書き、旧changeの decisions.md の該当Qにも `→ <version> の Qn で置換` を追記する（archives 配下でも追記する） |

## E. 承認前の点検

| ID | 強度 | 規約 |
|---|---|---|
| D-11 | MUST | 「未決定」が残ったまま承認済みにしない |
| D-12 | SHOULD | 本文に最終更新日や陳腐化する状態を書かない（日付は根拠の確認日と承認日だけにする） |

## 例の作り方

本規約に載せるOK/NG例は作例にする。実在する decisions.md は引用しない（引用元が後で変わるとノイズになるため）。
