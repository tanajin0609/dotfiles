# Design: feat-todo-propose-checker

## アーキテクチャ

### 書き換え対象: `todo-propose.md` の「## today-todoバッチモードの最終レビュー（敵対的検証）」節

現状（180〜198行目）は以下の構造。

```
バッチモードで全サブエージェントの報告（0-4）が揃ったら、メインセッション自身が忖度なしで
検証する（サブエージェントの自己申告をそのまま信用しない）。少なくとも以下を疑う。
  - 「新規提案が必要」の起票内容
  - 「対象外」判定
  - ディレクトリ/todo.mdへの追記
  - 見出し破壊
疑わしい点が見つかった場合は、該当サブエージェントの成果物を直接読み直して裏取りする...
この検証を終えてから「## 3. 完了報告と停止」の内容をサブプロジェクトごとに集約して報告する。
```

これを `todo-execute.md` Step4 と同型の構造に置き換える。

```
バッチモードで全サブエージェントの報告（0-4）が揃ったら、`todo-propose-checker`エージェント
（`Write`・`Edit`を持たない専任の検証エージェント。定義: `~/.claude/agents/todo-propose-checker.md`）を
**新規コンテキストで**起動し、各サブエージェントの報告を鵜呑みにせず成果物をゼロから再検証させる。
0-2でサブエージェントを並列起動した張本人であるメインセッションが同じコンテキストで検証すると、
評価が甘くなりやすいため、判定は起票と別コンテキストのCheckerに分離する。

`todo-propose-checker`に渡すもの:
  - 0-4の全サブエージェント報告（項目内容・分類・作成/更新ファイルパス・調査結果の要点）
  - 入力元の todo-YYYY-MM-DD.md へのパス

`todo-propose-checker`は少なくとも以下を自分で確認する（詳細な検証観点はエージェント定義側に
持たせ、本コマンドでは重複させない）:
  - 「新規提案が必要」の起票内容に、手順2の調査結果として書かれたファイルパス・コマンドが
    実在し、記述と一致するか
  - 「対象外」判定が0-3の基準表に照らして妥当か（恣意的な回避でないか）
  - 既存ディレクトリ流用の原則（A-1/B-1）を破って重複作成していないか
  - A-3（dev系）のtodo.md追記が実際に行われているか
  - proposal.md/design.md/order.md/plan.mdの既存見出しを変更・削除していないか

`todo-propose-checker`が「要修正」と判定した項目は、指摘内容を添えて該当サブプロジェクトの
サブエージェントに差し戻し、再起票させたうえで再度`todo-propose-checker`にかける（合格するまで
0-2↔本節を繰り返す。2周しても解消しない場合はループを打ち切り、ユーザーに判断を仰ぐ）。

メインセッションは`todo-propose-checker`の判定もそのまま鵜呑みにせず、疑わしい点があれば自分でも
成果物を読み直して裏取りする。

この検証を終えてから「## 3. 完了報告と停止」の内容をサブプロジェクトごとに集約して報告する。
```

`todo-execute.md` Step4 との対応関係:

| `todo-execute.md` | `todo-propose.md`（本提案） |
|---|---|
| Step2のサブエージェント（Maker） | 0-2のサブエージェント（Maker） |
| `todo-checker`（Checker） | `todo-propose-checker`（Checker、新規） |
| 検証観点5項目（テスト実行・delta spec diff・plan.md承認・スコープ逸脱・todo.md反映） | 検証観点4項目（調査の実在形跡・「対象外」判定の恣意性・既存流用原則・todo.md追記/見出し破壊） |
| 要修正時はStep2に差し戻し、2周で打ち切り | 要修正時は0-2に差し戻し、2周で打ち切り（同じ設計を採用） |

### 新規: `todo-propose-checker` エージェント定義

配置は `todo-checker.md` と同じ方式（dotfilesリポジトリが実体、`~/.claude/agents/` へ symlink）。
実パスは実装時に `dotfiles-sync` skill の管理対象ディレクトリを確認して決める
（`todo-checker.md`の実体パスに準じる想定）。

## 実装方針

### エージェントの役割・ツール構成

`todo-checker.md`（`tools: Read, Grep, Glob, Bash`、判定専任・修正不可）をテンプレートに、
`/todo-propose` 固有の検証観点に差し替える。

```yaml
---
name: todo-propose-checker
description: |
  `/todo-propose`（引数なし・バッチモード）の「today-todoバッチモードの最終レビュー」専任の
  Checker。起票した本人（0-2のサブエージェントやメインセッション）とは独立した新規コンテキストで、
  各サブプロジェクトへの提案書・作業計画書の起票内容をゼロから再検証する。判定のみが役割で、
  ドキュメントの修正は行わない。
tools: Read, Grep, Glob, Bash
---
```

`Write`・`Edit`を与えない理由は`todo-checker.md`と同じ（見つけた不備を自分で「直して合格にする」
ことを構造的に禁止し、判定と修正を分離する）。

### 検証観点（`todo-checker.md`の書式を踏襲し、`/todo-propose`固有の4項目に翻案）

`todo-propose.md`の既存4項目（180〜193行目）を、Checker自身が実行可能な確認手順に具体化する。

1. **起票内容に調査の実在した形跡があるか**
   - 「背景」「調査結果」に書かれた参照ファイルパスを`Read`で開き、実在するか・記述内容と
     一致するかを確認する
   - 「`git branch -a`で確認した」等のコマンド言及があれば、Checker自身が`Bash`で再実行し、
     出力が報告内容と整合するか確認する
   - 推測で埋めた記述が断定表現になっていないか（「〜と思われる」等の推測表現なしに
     未確認事項が事実として書かれていないか）を文面レベルで確認する
2. **「対象外」判定が恣意的でないか**
   - 0-3の基準表（新規提案が必要／既に提案済み・進行中／人間の決定待ち／物理作業）に照らし、
     「既に提案済み・進行中」ならその`docs/changes/`・`order-*/`が実在し内容が埋まっているかを
     `Read`で確認する
   - 「人間の決定待ち」「物理作業」の理由が具体的か（一般論での回避でないか）を確認する
3. **既存ディレクトリ流用の原則を破っていないか**
   - 新規作成された`docs/changes/`・`order-yyyymmdd/`について、同じ変更内容を扱う既存ディレクトリが
     他にないか`Glob`・`Grep`で対象サブプロジェクトを探索する
4. **`todo.md`追記が実際に行われているか**
   - dev系: 対象サブプロジェクトの`docs/tasks/todo.md`を`Read`し、A-3の書式
     （`- [ ] <change-name> — 提案中・承認待ち → ...`）で実際に1行追記されているかを確認する
   - ops系: `todo.md`（`B-4`）が追記されているか同様に確認する
5. **見出し破壊がないか**
   - 更新された`proposal.md`/`design.md`/`order.md`/`plan.md`を`_templates/dev/docs/changes/<change-name>/`・
     `_templates/ops/`の雛形と見出しレベルで比較し、既存見出しの変更・削除・並び替えがないか確認する

（4・5は`todo-checker.md`の「`docs/tasks/todo.md`が実際に更新されているか」観点と同型。
1〜3は`/todo-propose`固有で新設）

### 報告フォーマット

`todo-checker.md`と同型を採用する。

```
- 検証した項目ごとに: 確認方法（実行したコマンド／読んだファイルパス）と結果
- 疑わしい点・虚偽・過剰申告が見つかった場合は、具体的な根拠（ファイルパス・行・コマンド出力）
  とともに明示する。黙って見逃さない
- 総合判定: 合格 / 要修正（要修正の場合は何をどう直すべきかを具体的に指摘する。ただし自分では直さない）
```

### 呼び出し元の変更点（`todo-propose.md`）

- 節見出し「## today-todoバッチモードの最終レビュー（敵対的検証）」は維持する（見出し破壊をしない）
- 本文を上記「アーキテクチャ」節の置き換え案に差し替える
- 「## 3. 完了報告と停止」冒頭の「（バッチモードでは、上記「today-todoバッチモードの最終レビュー」を
  経たうえで...）」という参照文はそのまま使える（変更不要）

### 確認事項（design側、推測で決めず質問として残す）

1. **要修正時の再起票フロー**: `todo-execute.md`は「Step2↔Step4を繰り返す（2周で打ち切り）」という
   具体的なリトライ上限を明記している。本提案でも同じ「2周で打ち切り、ユーザーに判断を仰ぐ」を
   踏襲したが、`/todo-propose`バッチモードは0-2で一度に全サブプロジェクトを並列起動しているため、
   「要修正」になった**特定のサブプロジェクトだけ**を再起動する設計になる。この部分は
   `todo-execute.md`側にも明文化された手順が無く、今回新規に補う必要がある
   （再起動時に他のサブプロジェクトの結果を巻き込まない、という前提で良いか要確認）。
2. **`todo-propose-checker`のモデル選定**: `todo-checker`エージェント定義にはモデル指定の記載が
   見当たらなかった（`~/.claude/agents/todo-checker.md`にfrontmatterの`model`項目なし、
   デフォルト挙動に委ねている）。`todo-propose-checker`も同様にモデル未指定でよいか、
   `model-routing` skillの基準（判断・統合系タスクはダウングレードしない）に従って明示指定するかは
   実装時の判断事項として残す。
3. **単一対象モードへの適用有無**: 本提案は「today-todoバッチモードの最終レビュー」節のみが対象。
   `/todo-propose`の単一対象モードには同種の敵対的検証ステップがそもそも存在しない
   （`todo-propose.md`全文を確認済み）。単一対象モードにも同様のCheckerを導入すべきかは
   本提案のスコープ外とし、別途の判断に委ねる。
