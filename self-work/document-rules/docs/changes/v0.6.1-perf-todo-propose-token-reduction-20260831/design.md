# Design: perf-todo-propose-token-reduction

## アーキテクチャ

現状: サブエージェント（0-2で並列起動）→ 親セッションへ詳細報告（0-4）→ 親セッションの会話に
全項目分蓄積 → `todo-propose-checker`へ親セッション経由で報告一式を渡す、という一直線の
データフロー。親セッションが「全項目の詳細のハブ」になっている点がボトルネック。

変更後: サブエージェントは担当項目の成果物ファイルへの書き込みを完了させた後、親セッションへは
要約のみを返す。`todo-propose-checker`はサブエージェントの報告要約ではなく、成果物ファイルの
パス一覧を受け取り、各ファイルを自分で読みに行く。親セッションは「どこに何が書かれたか」の
索引だけを持てばよく、詳細を経由させない。

```
[変更前]
サブエージェント(詳細報告)──→ 親セッション(全詳細を蓄積) ──→ Checker(親経由で受け取る)

[変更後]
サブエージェント(成果物ファイルに直接記入) ──┐
                                              ├─→ 親セッション(パス+分類+1行要約のみ)
                                              └─→ Checker(ファイルを直接読む)
```

## 実装方針

`todo-propose.md`の以下の節を変更する。

- **0-2（サブエージェントへの指示）**: 「担当項目一覧」「0-3の判定基準」「該当する場合は
  ワークフロー（手順1・2、A/B、C）を実行」に加え、「0-4の報告は成果物ファイルへの反映を
  終えた後に、親への返答としては要約のみ返すこと」を明記する。
- **0-4（報告フォーマット）**: 現行の「項目内容・分類・作成/更新ファイルパス・調査結果の要点・
  リスク/質問・Notion書き戻し結果」のうち、親セッションへの返答に含めるのは
  「項目内容（見出し用）・分類・作成/更新ファイルパス」のみとする。調査結果の要点・リスク/
  質問・Notion結果は成果物ファイル側（`proposal.md`の各見出し等）に書かせ、親には転記させない。
- **今日のゴールとマイルストーン最終レビューの節（L195-230）**: `todo-propose-checker`への
  引き渡し内容を「0-4の全サブエージェント報告」から「作成/更新ファイルパス一覧＋入力元
  `todo-YYYY-MM-DD.md`へのパス」に変更する。Checker側の検証観点（記述と実ファイルの一致、
  対象外判定の妥当性等）は変更しない——参照元をファイル直読みに変えるだけ。
- **3-1（まとめ版の書き出し）**: 現行はメインセッションが「1〜6は完了報告と同じで新しい判断を
  足さない」としているが、この節で使う情報も親セッションの会話上の詳細ではなく、各サブプロジェクトの
  成果物ファイルを都度読みに行く形に変える（親セッションが会話中に保持する情報量を増やさない）。

## 削減効果の検証（2026-09-04）

ダミーコード・ダミー項目1件を対象に、報告方式を3パターン用意して比較した。

1. Before（現行）: サブエージェントが親へ調査結果・リスク等を全詳細で報告
2. v0.6.1（本提案）: サブエージェントは成果物ファイルに詳細を書き、親へは分類・パス・1行要約のみ返す
3. 参考: Zenn記事「SKILL.state」のアイデアを追加で乗せた案（親への自然文報告をやめ、
   構造化状態ファイル（JSON）へのパッチ書き込みのみで完結させる）

| | サブエージェント自身のtokens | 親への報告文サイズ | Checker側のtokens |
|---|---|---|---|
| Before | 36,223 | 1,705字 | 42,588 |
| v0.6.1（本提案） | 36,082 | 135字（92%減） | 36,663 |
| 参考: SKILL.state拡張案 | 36,581 | 3字（99.8%減） | 40,022 |

**結論**:

- サブエージェント自身の調査コストは報告方式によらず一定（同じファイルを読んで同じ調査をするため）。
  差が出るのは親セッションに蓄積される報告文の量のみ。
- v0.6.1の「要約1〜2行を返す」方式だけで親側の蓄積は92%減となり、25並列×72項目のバッチに換算すると
  8月末に実測された親側cache_read tokensの異常値（3,857万）の主要因を解消できる見込み。
- 参考として試した「SKILL.state」方式（自然文報告ゼロ・JSON状態ファイルのみ）は、親側の蓄積を
  さらに99.8%減まで削れるものの、Checkerが状態ファイル経由で成果物ファイルを辿る手間が増え、
  Checker側のtokensはv0.6.1より悪化した（36,663→40,022）。v0.6.1で親側の蓄積は既に十分小さく
  なっているため、この上乗せ分の追加実装コストに見合うメリットは今回の検証では確認できなかった。
  **今回のスコープには含めない。**
- サンプル数1項目のみの検証であり、数値は参考値。傾向（v0.6.1で大部分が解消される・追加の
  構造化はコストに見合わない）を裏付けるものとして扱う。
