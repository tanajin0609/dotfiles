# Proposal: perf-todo-propose-token-reduction

## 背景

2026-08-31、`/todo-propose`バッチモード（25サブプロジェクト・72項目）のトークン消費を実測した。
親セッション（司令塔）と25並列サブエージェント＋`todo-propose-checker`の合計で、cache_read
input tokensが約6,121万（親38,578,191＋サブエージェント計22,630,282）に達し、同日実行した
全セッション中で最大だった。当初「日をまたいで1セッションを使い回す運用習慣が原因」という
仮説を立てたが、同日中に新規セッションで実行した今回のケースでも同程度に重かったため、この
仮説は棄却した。実測から、原因は`/todo-propose`バッチモードの構造そのものにあると判断した。

具体的な要因（`$HOME/.claude/commands/todo-propose.md`の該当箇所）:

1. L84-92: 各サブエージェントの詳細な調査結果・報告を親セッションに直接返させており、
   親セッションの会話履歴に全項目分の詳細が蓄積され続ける。
2. L108-119: 一次判定（0-3）前に「既存資材の調査（省略禁止）」を全項目に対して同じ深さで
   実行しており、「対象外」「決定待ち」に分類される項目にもフル調査コストがかかっている。
3. L195-230: `todo-propose-checker`が全サブエージェントの報告を独立コンテキストで
   ゼロから読み直す二重検証構造になっている。

## 提案内容

上記3要因のうち、既存の安全策（過剰生成よりも保留を優先する運用ルール、二重検証による
自己採点回避）を弱めずに実施できる要因1への対応を今回のスコープとする。

- サブエージェントは担当項目の詳細な調査結果・報告を、親セッションへの返答としてではなく
  対象サブプロジェクトの成果物ファイル（`proposal.md`/`design.md`/`tasks.md`または
  `order.md`/`plan.md`）に書き込む。
- 親セッションへの返答は「サブプロジェクト名・分類・作成/更新ファイルパス・1行要約」のみに圧縮する。
- `todo-propose-checker`は親経由の詳細報告ではなく、各サブエージェントが書いた成果物ファイルを
  直接読んで検証する（既にファイルをゼロから読み直す設計のため、参照元を変えるだけで検証の
  厳密さは変わらない）。

要因2（一次判定前のフル調査の要否）・要因3（Checkerの検証対象を新規起票分のみに絞る）は、
既存の安全策とのトレードオフが大きいため今回のスコープ外とし、必要なら別途提案する。

## 影響範囲

- `$HOME/.claude/commands/todo-propose.md`
  （0-2〜0-4のサブエージェント指示・報告フォーマット、L195-230のChecker入力）
- 影響を受ける成果物: バッチモードで生成される全サブプロジェクトの`proposal.md`/`design.md`/
  `tasks.md`/`order.md`/`plan.md`（見出し・書く内容自体は変更しない。書き込みタイミングが
  「親への報告後」から「サブエージェントが直接書く」に変わるのみ）
- 単一対象モード（`$ARGUMENTS`あり）は影響を受けない（並列サブエージェントを使わないため）
