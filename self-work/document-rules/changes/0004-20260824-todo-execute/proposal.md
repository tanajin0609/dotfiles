# 提案書: `/todo-execute` の新設（承認済みマイルストーンの実装）

> 対象読者: document-rules.md / `/todo-execute` のメンテナ（自分）
> スコープ: `today-todo/plan-YYYY-MM-DD.md`（既存定義済みだが専用コマンドが無かった実行計画）を
>   `/todo-execute` が正式に生成・実行するようにする
> 元セッション: 2026-08-24、`changes/0003-20260824-work-log-and-milestone`で保留した未決事項
> 結論: **決定・本セッション内で反映済み**

## 1. 経緯

`0003`で`/todo-propose`バッチモードのまとめ版にマイルストーン提案（`M1`/`M2`…、対象サブプロジェクト・
モデル・エフォート付き）を追加した。その提案を実際に実装するコマンドが無かったため、ユーザーから
「`/todo-execute`を作ろう」という依頼があったが、承認判定の粒度（マイルストーン単位か・ゴール単位か・
proposal全体か）が未確定だったため、`0003`ではこの点を保留していた。

`0003`反映後、ユーザーに確認し、**マイルストーン単位（`M1`, `M2`...）で`$ARGUMENTS`に明示指定する**
方式に決定した。

## 2. 【決定】承認単位はマイルストーンID、指定は`$ARGUMENTS`必須

**深刻度: 中 / 確度: 高**

- `/todo-execute M1 M3`のように、実行時に対象マイルストーンIDを明示指定する。
- 引数なし実行では**実装を開始せず**、対象日付のproposalに載っているマイルストーン一覧を提示して
  停止する。「全部やる」をAIが自己判定することはない。
- 理由: `/todo-propose`自体が「承認は人間が行う、AIが自己判定して次工程に進まない」という原則
  （directry-rules.md 7章）を持っており、`plan.md`の承認状況チェックボックスのような外部ステータス
  ストアも無い。マイルストーン単位の明示指定は、この原則を実装フェーズにもそのまま延長する形で、
  ops系で以前検討して見送った「ステータス駆動のA/B分岐」を導入せずに済む。

## 3. 【決定】`plan-YYYY-MM-DD.md`は`/todo-propose`のproposalを転記するだけ、新しい判断を加えない

**深刻度: 低 / 確度: 高**

マイルストーンの分解・優先順位付け・モデル/エフォートの提案は`/todo-propose`の責務のまま。
`/todo-execute`はStep1で指定マイルストーンをサブプロジェクト単位にグルーピングし、ファイル競合マップと
実行順序を`plan-YYYY-MM-DD.md`に書くだけで、優先順位や分解をやり直さない（責務分割。過去に
`/apply`・`/archive`が未実装のまま責務だけ割り当てられ機能しなかった教訓（directry-rules.md 1章）を
踏まえ、本コマンドの責務を実装ステップだけに絞る）。

## 4. 【決定】実装は既存のSDDワークフロー・delta spec記録方式に乗せる（新方式を作らない）

**深刻度: 低 / 確度: 高**

dev系サブプロジェクトの実装は`projects/CLAUDE.md`の標準ワークフローと`directry-rules.md` 4.2の
delta spec記録方式（`docs/changes/<change-name>/specs/base/`への事前コピー→編集→diff化）を
そのまま使う。ops系は`plan.md`の承認状況チェックを確認し、未承認なら実装しない。
本コマンド専用の新しい記録方式・承認方式は作らない。

- `document-rules.md`: `plan-YYYY-MM-DD.md`の行・専用節・How to applyを`/todo-execute`前提に更新

  （引数・Step0〜5・注意事項。`/todo-propose`と対をなす構成）

  （0003側は追記せず、本ファイルへのポインタとして残す）
