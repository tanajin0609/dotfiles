# 提案書: `/todo-propose` バッチモードに横断まとめ版の出力を追加する

> 対象読者: document-rules.md / `/todo-propose` コマンドのメンテナ（自分）
> スコープ: バッチモードの成果物として `today-todo/plan-YYYY-MM-DD-todo-proposal.md` を追加し、
>   0001 で「作らない」と決めた範囲を一部改定する
> 元セッション: 2026-08-24、`/todo-propose` バッチモード実行後に
>   「まとめ版を today-todo に格納してって指示出してたじゃん」という指摘
> 結論: **決定・本セッション内で反映済み**（document-rules.md 本体・コマンド定義・当日分ファイルの
>   リネームまで同一セッションで実施）

## 1. 経緯

2026-08-24 に `/todo-propose` バッチモードを実行し、43件を6サブプロジェクトへ振り分けて
新規8件を起票した。その後「`today-todo/` にまとめ版が無い」と指摘された。

一次回答では「0001 の決定どおり `/todo-propose` は `today-todo/plan-*.md` を作らない仕様」と答えたが、
これは**ユーザーが以前出していた「まとめ版を格納して」という指示がコマンド定義に反映されていなかった**
ために起きた食い違いだった。過去セッションのログを全文検索しても該当指示の記録は残っておらず、
口頭ベースで定義化されないままだったと推定される（推定。ログに無い以上、断定はできない）。

## 2. 【決定】バッチモードのまとめ版は作る（0001 の一部改定）

**深刻度: 中 / 確度: 高**

0001 の2章は「`/todo-propose` の成果物は常に対象サブプロジェクト内に閉じ、サブプロジェクトを横断する
調整ファイルは作らない」と決めた。この原則のうち、**実装まで進める横断実行計画を作らない**という部分は
維持する。一方で**起票結果への入口となるまとめ版**は必要と判断し、追加する。

理由: バッチモードは1回で6サブプロジェクト前後・十数ディレクトリに成果物を生成する。
セッション最終報告はターミナルに流れて消えるため、承認判断の起点になるファイルが残らない。
「散らばった成果物への入口」は横断ファイルでしか成立しない（単一サブプロジェクトの
`docs/changes/` には置けない）。

まとめ版は**報告の写しであって新しい判断を足さない**。これにより「AIが承認前に方針を決めない」という
0001・directry-rules.md 7章の原則とは衝突しない。

## 3. 【決定】命名は `proposal-YYYY-MM-DD.md`

**深刻度: 低 / 確度: 高**

- 初版では `plan-YYYY-MM-DD-todo-proposal.md`（既存の `plan-YYYY-MM-DD-<topic>.md` 形式に乗せ、
  topic を `todo-proposal` に固定）としたが、直後に「`plan` と `proposal` を両方名前に含める意味が無い」
  と指摘され撤回した。`plan-` を残した理由（アーカイブ運用の `mv` 対象glob）は、
  そのglob自体を1行拡張すれば解消する話で、ファイル名を冗長にする理由にはならなかった。
- 採用案: **prefixを `proposal-` に変え、`plan-` は付けない**。実装を含む横断実行計画（`plan-YYYY-MM-DD.md`）
  とは prefix そのものが違うので、ファイル名だけで種別が判別できる（サフィックスに頼らない）。
- アーカイブ運用のglob（document-rules.md 該当節）に `proposal-YYYY-MM-DD.md` を追加し、
  `today-todo/`直下に置ける命名規則を3種（`todo-`・`plan-`・`proposal-`）に更新した。
- **`propose` ではなく `proposal`**（2026-08-24 ユーザー指示）。コマンド名は `/todo-propose`（動詞）だが、
  ファイルが指すのは成果物なので名詞形に揃える。
