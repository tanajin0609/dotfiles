# 提案書: セルフランナー（無人定時実行）導入の検討

> 対象読者: document-rules.md のメンテナ（自分）
> スコープ: Qiita記事（AIタスク管理ワークフロー事例）が紹介していた「無人定時実行」を
>   `todo-import → todo-propose → todo-execute` ワークフローに導入するかどうかの検討
> 元セッション: 2026-09-02
> 結論: **決定・導入しない**（選択肢A。2026-09-02ユーザー決定。理由は「4. 決定内容」参照）

## 1. 経緯

記事は`ScheduleWakeup`/`CronCreate`相当の仕組みで15分間隔にタスクキューを消化する
「セルフランナー」を紹介しており、拘束時間の中央値やPRマージまでの時間を大きく改善したと
報告している。一方で「完了定義の分解」「テスト足場の前提」「時間厳守の未達」「人間の指示精度」
という課題も自己申告しており、無条件に良い仕組みではない。

現行の`todo-propose`/`todo-execute`は、承認（マイルストーン指定）・実装・Checker検証の
すべてが人間起動のセッション内で完結する設計になっている（`todo-execute.md`「注意事項」:
「引数なし実行で『全部やる』をAIが自己判定することはない」）。無人定時実行を導入すると
この前提が崩れるため、まず**導入するかどうか自体**が論点になる。

## 2. 論点: 承認ゲートと無人実行をどう両立させるか

`/todo-execute`は「ユーザーが`$ARGUMENTS`でマイルストーンIDを明示指定した場合のみ実行する」
という設計（2026-08-24確定、`document-rules.md`参照）。これは「AIが自己判定して全件実行しない」
という既存原則そのものであり、無人定時実行はこの原則と正面から衝突する。

### 選択肢

| 選択肢 | 内容 | トレードオフ |
|---|---|---|
| A. 導入しない | 現行の人間起動フローを維持する | 記事が報告した拘束時間・レビュー往復数の改善効果は得られない。ただし承認ゲートの原則を変えずに済む |
| B. 事前承認済みマイルストーンのみ無人実行 | ユーザーが日中に`$ARGUMENTS`でマイルストーンIDを明示指定した「実行予約」を作り、`ScheduleWakeup`/`CronCreate`はその予約済みIDだけを定時実行する（新規のマイルストーン選定・承認は無人実行の対象にしない） | 承認ゲートの原則は保てるが、「予約」という新しい状態・データ構造が要る。Checkerが要修正判定した場合に無人セッションが誰の判断も仰げず止まる問題も残る |
| C. 提案（todo-propose）のみ無人実行、実装は人間起動のまま | `todo-propose`バッチモードだけ定時実行し、`today-todo/proposal-YYYY-MM-DD.md`を朝までに用意しておく。実装（`todo-execute`）は引き続き人間が指定 | 記事の「起動時に司令塔がタスクを提示する」部分だけ先取りできる。実装フェーズの拘束時間短縮効果は無いため、記事ほどの効果測定改善は期待できない |

## 3. 未決定のまま残る前提

- 安全装置（多重起動防止、時間枠での打ち切り、1区切りで停止）は、B/Cいずれを選んでも
  無人実行を採用するなら別途設計が必要（本提案の対象外。導入方針が決まってから着手する）。
- `0009-20260902-defer-loop-safeguards`のdefer運用（回数上限等）が固まっていないと、
  無人実行下でdeferの無限先送りが起きた場合に誰も気づけないリスクが増す。導入するとしても
  `0009`の決定が先。

## 4. 決定内容

**選択肢A（導入しない）を採用**。現行の人間起動フロー（`todo-propose`/`todo-execute`とも
ユーザーの明示指示でのみ実行）を維持する。関連ファイルへの変更は無し（現状維持のため）。

再検討する場合は、`0009`のdefer安全装置が実運用で機能しているかを確認してからにする
（`0009`の「未決定のまま残る前提」参照）。
