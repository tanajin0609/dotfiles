## 3. 【決定】作業用ディレクトリの正式名は `refs`

**深刻度: 高 / 確度: 高**

- `_templates/dev/docs/shared/` が既に汎用テンプレートの標準ディレクトリとして存在する。
- 実際に `docs/shared/` を使っているサブプロジェクトが5つある: `task-management` `notion-task-pipeline`
  `<ops-project-b>` `<ops-project-a>` `<ops-project-c>`。
- <project-a>だけが `docs/tmp/` を使っている outlier であり、しかも仕様書側の参照は
  `docs/shared/...` になっている（＝実装ミスで tmp を使い、shared という「意図した名前」に
  リンクが揃っている状態）。

このまま「tmp固定」を directry-rules.md の汎用ルールとして書くと、既存5プロジェクトの命名と
食い違う新ルールを追加することになり、**今回問題にしている「命名不一致でリンクが壊れる」現象を
directry-rules.md自身が量産する**ことになる。

**検討した選択肢**:

1. <project-a>だけの例外として `tmp` を許容し、汎用ルールには書かない。
2. 汎用ルール側を「tmp」に統一し、既存5プロジェクトの `docs/shared/` を将来的にリネームする
   （移行コストが発生する）。
3. `shared` に統一する（既存5プロジェクトの実績を正とする）。
4. 既存資産（`shared`/`tmp`）のどちらにも寄せず、新規名称 `refs` に統一する。

**決定（2026-08-13再ヒアリング）**: **4. `refs` に統一**。

判断理由:
- 対象ファイル（例: `data-inconsistency-report.md` のような棚卸し・検証レポート）は「一時的で
  消してよいもの」ではなく、仕様書（specs）側から継続的にリンクされる補足資料である。
- `tmp` は「一時的・消してよい」という語感が実態と矛盾し、これ自体が命名不一致・リンク崩壊の
  温床になりうる（<project-a>で実際に発生した状態）。
- `shared` は実態に近いが、`refs`（仕様書から参照される資料であることを直接示す）の方がより
  実態を表すと判断した。
- 既存5プロジェクト（`docs/shared/`）・<project-a>（`docs/tmp/`）とも将来的に `docs/refs/`
  へのリネームが必要になるが、移行作業自体は本書の対象外（6章参照）。

なお、名前をどちらにするかより、リンク切れを検出・修正する手順が無いことが本質的な原因という
認識（4章参照）に変わりはなく、4章の手順ルール化と両輪で扱う。

## 4. 「単一図への一元化」だけではリンク劣化を防げない

**深刻度: 中 / 確度: 高**

<project-a>の `docs/03-design/flow.drawio` は今回の懐疑フェーズで唯一実在する図だったが、
その図自身のテキスト注記が `docs/proposal.md`（実際は `docs/changes/proposal.md`）、
`docs/shared/data-inconsistency-report.md`（実際は `docs/tmp/`）という、**今まさに問題にしている
壊れたパスを図の中にすでに含んでいた**。

図解は文章より劣化しにくいわけではなく、むしろ `.drawio` は grep やリンクチェッカーが効きにくいため
劣化の検出が遅れる。したがって「構造的事実は単一の図に一元化する」ルールを追加する場合は、
**併せて「ドキュメント内の相対リンク・パス文字列を洗い出す手順」を持たせないと同じ問題が再発する**。

**提案する汎用ルール（案）**:

- 構造・レイアウトなど「見た目の事実」は単一の図（またはそれに準ずる1ファイル）を正とし、
  他文書からはリンクのみで参照する（2章の合意どおり）。
- ディレクトリ構成を変更した際（例: `docs/specs/` → `01-reqs/02-specs/03-design`、
  `docs/shared/` → 実体としての `docs/tmp/` など）は、**変更前のディレクトリ名・ファイル名で
  `grep -rn` を実行し、ヒットした全ファイル（`.md` だけでなく `.drawio` 等のテキスト内埋め込みも含む）
  のリンクを更新する**ことを完了条件に含める。

## 5. 壊せなかった点（過剰指摘にならないよう明記）

- **proposal.mdの多責務構成**: <project-a>の `docs/changes/proposal.md`（決定ログ／技術検証／
  アーキテクチャ提案／棚卸し結果／フェーズ計画／未決事項などが1ファイルに混在）について、
  5章の棚卸しサマリを実際に193行の詳細レポート（`data-inconsistency-report.md`）と比較したが、
  要約→詳細への健全なリンク階層になっており、内容の重複は見つからなかった。
  「複数責務が1ファイルに混在していても、重複がなければ問題ない」という判断は支持できる。
- **01-reqs/02-specs/03-design 間の相互参照**: 直近で同時に編集されたこの3ディレクトリ間の
  リンクは実際に機能しており、破綻していない（tmp/・proposal.md・todo.mdとは対照的）。
- **ルート直下のDESIGN.mdとui-style-spec.mdの責務境界**: `.sp-*` はpreview-spec.md、それ以外は
  DESIGN.md由来、と表で明確に線引きされている。「唯一の正解」原則自体は破られていない
  （場所がdocs外なだけ）。
