# self-improve と Warp 流自己改善ループの比較

## 出典

Warp社のブログ記事（著者: Michael Segner、2026-08-26公開）。Claude Platform上で構築した
コードレビュー / Issueトリアージエージェントの自己改善事例。

## Warp流の自己改善ループの構成

- **内側スキル（ベーススキル）**: ドメイン知識・指示を保持する。タスク実行時に毎回使われる。
- **人間のフィードバック**: PR/Issueコメントなど、人間が既に作業している場所で低摩擦に取得する。
  「何を期待したか」だけでなく「なぜ」を含めるほど改善が効く。
- **外側スキル（インプルーバー）**: タスクごとではなくスケジュールで実行される観察エージェント。
  蓄積されたフィードバックとベーススキルの差分を見て、ベーススキルへの小さく焦点を絞った編集を
  PRとして提案する。
- 人間がPRをレビュー・承認してマージ → 次回のベーススキル実行から反映される。

## この環境での実現性

| Warp記事の要素 | 実現性 | 現状 |
|---|---|---|
| 内側スキル（ベーススキル） | 既にある | `code-review-checklist` 等の既存skillがこれに相当 |
| 人間フィードバックの低摩擦な取得 | 作れる | `gh api` でPR/Issueコメント取得は可能。専用スクリプトは未実装 |
| フィードバックの永続蓄積 | 既にある | auto memory（feedbackタイプ）、`track-issues` skill |
| スケジュール実行の観察エージェント | 作れる | `schedule` skill / `CronCreate` |
| ベーススキルへの焦点を絞った編集提案 | 既にある（近い形） | `self-improve` commandが担うが、蓄積フィードバックからの自動提案ではない |
| PR経由の人間承認 | 一部作れる | dotfilesはgit管理。現状は直接push運用（git-drillにより commit/push は手動） |
| 検証環境でのチューニング | 既にある | `skill-creator` のeval機能、コード領域は既存テスト |
| 組織指標（マージ時間・貢献者数等）の追跡 | 意味が薄い | 個人利用のため該当する指標がほぼ無い |

## ギャップ

現状の `self-improve` commandは「skill/promptを新規作成・大幅改訂した直後に、白紙subagentへ
シナリオを実行させてバイアス排除評価する」一発起動型。Warp型との差分は次の1点:

- 評価のベースライン準備（ワークフロー手順1）で使うシナリオが「想定シナリオの新規作成」のみで、
  実際に蓄積された人間フィードバック（memoryのfeedbackタイプ、`track-issues` のissue.md）を
  シナリオ設計の入力に使っていない。

スケジュール実行やPR承認フローは個人利用の現状では過剰（Warpは複数人・OSSリポジトリ前提）。
無理に自動化せず、「手動起動時に蓄積フィードバックも参照する」程度の最小追加に留める。
