# track-issues — 問題リアルタイム記録

冒頭で `/home/igpf-2500009/.claude/local/doc-rules/RULES.md` が存在すれば Read し、ドキュメント横断ルールを確認してから実行する（存在しない環境では無視して続行する）。

作業中に発生したバグ・問題を `issue.md` に段階的に記録する。
発生時は「事象」のみ、原因判明時に「原因」、解決時に「修正内容」を追記していく。

記録を後回しにすると、原因にたどり着くまでに試した経路や途中で捨てた仮説が失われる。
そこが後から「なぜこの実装にしたか」を説明する材料になるため、その場で書き足していく。

---

## Step 1: 起動時の動作

カレントディレクトリの `issue.md` を Read で読み込む。

- **存在する場合:** 既存 Issue の一覧・ステータスを把握し、未解決 Issue があればユーザーに通知する
- **存在しない場合:** 「issue.md はまだありません。問題が発生したら即座に記録します。」と伝える（空ファイルは作成しない）

起動後は以下のトリガー条件を常時監視しながら作業を継続する。

---

## Step 2: トリガー条件（自律的に記録するタイミング）

ユーザーの指示を待たず、以下の状況で即座に issue.md を更新する。

### 発生検知 → 新規 Issue 追加

- ターミナル・ログ・コードにエラー・例外・想定外の動作が現れた
- ユーザーが「なぜ〜なのか」「〜がおかしい」「〜が動かない」と発話した
- 実行結果がドキュメントや設計の仕様と一致しない

### 調査進展 → 原因セクションを追記

- 原因の仮説をユーザーが口にした、またはコードから根本原因が判明した
- 調査コマンドの出力から原因が特定できた

### 解決 → 修正内容を追記・ステータス更新

- 修正を適用してエラーが消えた・動作が正常になった
- ユーザーが「直った」「解決した」「この修正で OK」と発話した
- 別の Issue 対応によって副次的に解決した

---

## Step 3: 記録ワークフロー

### 問題発生時（新規 Issue 追加）

`issue.md` の**先頭**（既存 Issue より上）に追記する。
この時点では「原因」「修正内容」セクションは書かない。

```markdown
# Issue: {タイトル}

**発生日:** YYYY-MM-DD
**ステータス:** 進行中

---

## 事象

{現象の説明。ログ・エラーメッセージをコードブロックで引用する}

---
```

### 原因判明時（原因セクションを追記）

該当 Issue の「事象」セクション後に追記し、ステータスを `調査中` に更新する。

```markdown
**ステータス:** 調査中   ← 更新

## 原因

{根本原因の技術詳細。コード・プロセス連鎖図・コマンド出力を含む}

```
プロセス連鎖図の例:
関数A → 例外発生
  → catch {} がキャッチ
  → ループ継続
```

---
```

### 解決時（修正内容を追記・ステータス更新）

「修正内容」セクションを追記し、解決日・ステータスを更新する。

```markdown
**解決日:** YYYY-MM-DD   ← 追加
**ステータス:** 解決済み  ← 更新

## 修正内容

{対策の技術説明}

**削除した機能:** {削除した処理・コード。なければ「なし」}

**残した機能:** {意図的に残した処理とその理由}

**設計判断:** {なぜその実装にしたか。代替案を検討して却下した理由があれば記載}

---
```

---

## フォーマット規則

| 項目 | 規則 |
|---|---|
| 記録順 | 新しい Issue を先頭に追加（降順） |
| Issue 区切り | 各 Issue の末尾を `---` で閉じる |
| ステータス値 | `進行中` / `調査中` / `解決済み` / `解決済み（後続 Issue により対策が変更された）` |
| ファイル場所 | コマンド実行時のカレントディレクトリ直下 |

---

## 注意事項

- **推測を書かない:** 「原因」は判明した事実のみ記載する。仮説段階では書かない
- **根拠を明記する:** コード・ログを引用する所見にはファイルパス・行番号を添える。直接検証していない内容は「確認済み」と書かない
- **PIIマスクを適用する:** 個人情報を含む値は、冒頭で読み込んだ doc-rules の PII 規則に従ってマスク表記へ変換してから記載する。規則が読めなかった場合は、実データらしき値をそのまま書かずユーザーに確認する
- **設計判断を省略しない:** 「削除した機能」「残した機能」「設計判断」は将来の変更判断の根拠になるため必ず記載する
- **クロス参照:** 一つの Issue が別の Issue の原因になった場合は両方に参照を記載する（例: `→ Issue「タイトル」を参照`）
- **記録後の通知:** issue.md 更新後は「Issue を追記しました: {タイトル}（{ステータス}）」とユーザーに伝える
