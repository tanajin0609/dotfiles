# 観点別チェックリスト

出典: Googleエンジニアリング・プラクティス「コードレビューで何を見るか」
(https://fujiharuka.github.io/google-eng-practices-ja/ja/review/reviewer/looking-for.html)

各観点について、確認すべきことと判断基準を要約する。

**常時評価**: 設計・機能性・複雑性・命名・一行ずつ・コンテキスト。
**合図付き**: 各節冒頭の `合図:` が差分に現れたときだけ評価し、1つも無ければ節ごと飛ばす
（合図の照合は機械的に、違反かどうかの判断は読んで行う）。
linter/CI が担保している事項（フォーマット・未使用import等）は全観点で指摘しない。

## 設計

もっとも重要な観点。個々のコードの正しさより先に、変更の設計そのものを見る。

- CLの各部分は相互にきちんと連携しているか
- この変更はこのコードベースに属するものか、それとも別のライブラリに切り出すべきか
- システムの他の部分とうまく統合するか
- この機能を追加するタイミングは今がふさわしいか

## 機能性

- 開発者の意図通りに動作するか。その意図はエンドユーザー・将来このコードを使う開発者
  双方にとって適切か
- 並行処理の項目は合図（`go ` `goroutine` `async` `await` `Promise.all` `Thread` `Lock` `mutex` `chan` `synchronized` 等）があるときだけ深く見る
- エッジケース・並行処理の問題（デッドロック、競合状態）をコードを読むだけでは
  見つけられないことを前提に確認する
- UI変更などユーザー影響のある変更は、可能なら実際に動かして確認するか、
  デモを依頼する
- 並行処理はレビュー・実装いずれも複雑さが跳ね上がるため、そもそも競合状態や
  デッドロックが起こりうる設計を避けられないかも検討する

## 複雑性

- 一行・関数・クラスそれぞれのレベルで「複雑すぎないか」を見る。複雑すぎる＝
  読んですぐ理解できない、または将来の呼び出し・修正で不具合を生みやすい
- 特にオーバーエンジニアリングを警戒する：現在必要な問題ではなく、将来発生するかも
  しれない推測上の問題に対応するための一般化・機能追加をしていないか
- 「将来の問題は発生してから対処すればよい」という原則で判断する

## テスト

合図: テストファイル（`test`/`spec` を含むパス）の変更、またはプロダクションコードの分岐・関数の追加


- 変更に見合った単体・結合・E2Eテストが、原則としてプロダクションコードと同じCLに
  含まれているか（緊急対応時のみ例外）
- テストが正確・適切・有用かを人間が判断する（テストのためのテストは書かない）
- コードが壊れたときにテストがきちんと失敗するか、逆に誤検知（flaky）を起こさないか
- 各テストがシンプルで有用なアサーションを持ち、テストメソッドとして適切に分割されているか
- テストコードも保守対象であることを踏まえ、複雑さを許容しない

## 命名

- 何であるか／何をするかを伝えるのに十分な長さがあり、かつ読みづらくないほど短いか

## コメント

合図: 追加行にコメント記号（`//` `#` `/*` `"""` 等）、または `TODO|FIXME|XXX`


- コードの「なぜ」を説明しているか。「何をしているか」の説明はコード自体をより
  シンプルにすることで不要にできないか（正規表現や複雑なアルゴリズムなど例外はある）
- 不要になったコメント（古いTODO、もう当てはまらない注意書き）が残っていないか
- クラス・モジュール・関数のドキュメンテーションコメント（目的・使い方・挙動）と、
  実装上のなぜを説明するコメントは役割が違うことを踏まえて評価する

## スタイル

合図: 1ファイルで変更行の過半が空白・改行・並び替えのみ（整形混在の疑い）。それ以外の好み・規約違反は linter に委ねる


- プロジェクトのスタイルガイドに沿っているか
- スタイルガイドに明記のない純粋な好みの問題（空白の使い方等）は、前例がなければ
  CL作成者のやり方を尊重する。個人的な好みで承認をブロックしない
- スタイル上の大きな変更（全体再フォーマット等）が機能的な変更に混在していないか
  （混在している場合はCLを分けるよう提案する）

## ドキュメンテーション

合図: ビルド・CI・設定・依存定義（`Makefile` `Dockerfile` `*.yml` `package.json` `go.mod` 等）、公開API、CLI引数の変更、またはファイル・関数の削除


- ビルド・テスト・相互連携・リリース方法を変える変更なら、README・仕様書・
  自動生成ドキュメント等の更新漏れがないか
- コードの削除・非推奨化に伴い、対応するドキュメントも削除すべきか検討する

## 一行ずつ

- 自動生成コード・データファイル・巨大なデータ構造以外は、人間が書いた行を
  実際に一行ずつ読む。書いてあることを鵜呑みにしない
- コードが読みにくくレビューが進まない場合、無理に読み解こうとせず、
  開発者にコードの明確化を依頼する

## コンテキスト

- 変更差分の周辺だけでなく、ファイル全体・システム全体に置いたときにどう見えるかを確認する。
  ただし読む範囲は、変更箇所の呼び出し元・呼び出し先と合図でヒットした箇所までに留め、差分と無関係なコードを網羅的に読まない
- 小さな変更でも、それが属する関数やシステム全体の健康状態を悪化させていないかを見る

## 良いこと

- 指摘だけでなく、良い設計・良いテスト・レビュー指摘への的確な対応など、
  良い実践を見つけたら伝える。メンタリングの観点では、間違いの指摘より価値がある場合がある
