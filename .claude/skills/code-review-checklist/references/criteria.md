# 承認基準・コメントの書き方

出典: Googleエンジニアリング・プラクティス「コードレビューで何を見るか」

## 最上位原則

コードレビューの主な目的は、コードの全体的な健康状態を時間をかけて改善すること。
一般に、CLが完璧でなくても、その変更がシステムのコードの全体的な健康状態を確実に
改善するとわかれば、レビュアーは積極的に承認すべき。ただし制限はある——たとえば
レビュアーが望んでいない機能を追加している場合は、コードがうまく設計されていても
承認を拒否してよい。

「完璧な」コードは存在しない。存在するのはより良いコードだけ。前に進める必要性と、
提案されている変更の重要性とをバランスよく検討する。システムのコードの健康状態を
悪化させると分かりきっているCLは、緊急事態以外では正当化されない。

## Nitの運用

重要でない指摘には "Nit: " というプレフィックスを付ける。これは「あら探し・細かい
指摘なので無視しても構わない」という意味であり、承認を保留する理由にはしない。
- スタイルガイドに明記のない純粋なスタイルの好み → Nit
- 教育目的のコメント（このドキュメントの基準を満たす上で重要でない） → Nitまたは
  「この CL で解決する義務はない」旨を明記

## メンタリング

コードレビューは開発者に新しいことを教える機会でもある。学びになるコメントは歓迎するが、
純粋に教育目的で基準達成に必須でないなら、Nitプレフィックスを付けるか義務でないことを
明記する。

## 判断の優先順位

1. 技術的な事実とデータが個人的な意見・好みに優先する
2. スタイルガイドに明記があればそれが絶対的な権威。明記がない純粋なスタイルの選択は
   個人の好みの問題であり、前例がなければCL作成者のやり方を尊重する
3. ソフトウェア設計の論点は基本的に純粋なスタイル・好みの問題ではなく、原則に基づく。
   複数の有効な選択肢がありCL作成者がデータや工学原理で同等に有効だと示せる場合は
   作成者の選好を受け入れる。そうでなければ標準的な設計原則で決める
4. 他のルールが適用されない場合、コードの健康状態を悪化させない限り、
   既存コードベースとの一貫性を求めてよい

## 意見の対立の解消

1. まずこのガイドラインとCL作成者ガイドに基づいてコンセンサスを目指す
2. 対立が特に強い場合は、コメントのやり取りより対面/オンラインミーティングの方が
   有効な場合がある（結果は必ずCLコメントに記録する）
3. それでも解決しない場合はエスカレーションする（チーム内議論、TL、コードの
   メンテナー、技術マネージャー）。合意に至らないままCLを放置しない
