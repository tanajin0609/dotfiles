# code-review-checklist

Googleエンジニアリング・プラクティスガイド「コードレビューで何を見るか」の観点をそのまま
チェックリスト化したレビューskill。詳細な原文の要約は `references/perspectives.md`、
承認基準やコメントの書き方（Nit運用・エスカレーション）は `references/criteria.md` を参照する。

## 最上位原則

CLが完璧でなくても、変更がシステムのコードの全体的な健康状態を確実に改善するとわかれば、
積極的に承認する。「完璧なコード」は存在しない——存在するのは「より良いコード」だけ。
指摘を出すことと承認を保留することは別。指摘が些細なら承認はブロックしない
（詳細: `references/criteria.md`）。

## 実行手順

1. **対象を特定する** — diff / PR番号 / ブランチ / パスのいずれかをレビュー対象として受け取る。
   対象が曖昧なら先に確認する。
2. **一行ずつ読む** — 自動生成コードや巨大データ構造以外は、変更行だけでなくファイル全体・
   呼び出し元も含めて実際に目を通す。読みにくくてレビューが進まないコード自体も指摘対象になる。
3. **観点ごとに確認する**（`references/perspectives.md` の各節を参照しながら）:
   - 設計（この変更はここに置くべきか、システム全体とどう統合するか）
   - 機能性（意図通りに動くか、エッジケース・並行処理の問題はないか）
   - 複雑性（オーバーエンジニアリングになっていないか、将来の推測に基づく実装をしていないか）
   - テスト（適切な単体/結合/E2Eテストがあるか、テスト自体の設計は妥当か）
   - 命名（短すぎず長すぎず、意味が伝わるか）
   - コメント（コードの「なぜ」を説明しているか、「何をしているか」の説明に留まっていないか）
   - スタイル（プロジェクトのスタイルガイド・既存コードとの一貫性）
   - ドキュメンテーション（README・仕様書等の更新漏れ）
   - コンテキスト（この変更をシステム全体の中に置いたときに健康状態を改善するか）
4. **指摘を分類する** — 修正必須の指摘と、"Nit: " を付けるべき些細な指摘（プロジェクトの
   スタイルガイドにない純粋な好みの問題や、教育目的のコメントなど）を区別する。
5. **良い実践があれば触れる** — 見つけた良い設計・良いテスト・レビュー指摘への的確な対応などは、
   findingsとは別に一言で伝える。あら探しだけのレビューにしない。
6. **ReportFindingsで報告する** — 修正が必要な指摘を `file` / `summary` / `failure_scenario` で
   まとめる。Nit相当の指摘は `summary` の先頭に "Nit: " を付ける。良い点の言及はReportFindingsの
   外（テキスト）で行う。

## 判断に迷ったら

- 承認可否・Nitの線引き・意見対立時のエスカレーション手順 → `references/criteria.md`
- 各観点で具体的に何を確認するか → `references/perspectives.md`
