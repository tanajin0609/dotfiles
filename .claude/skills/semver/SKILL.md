# semver — バージョン増分の判断

出典: https://www.tohoho-web.com/ex/semver.html（SemVer 2.0.0の日本語解説）

## 基本ルール

`MAJOR.MINOR.PATCH` の3点区切り。各要素は非負整数でゼロ埋め（`03`等）は不可。

- **MAJOR**: 後方互換性のない変更をしたとき
- **MINOR**: 後方互換性を保ったまま機能を追加したとき
- **PATCH**: 後方互換性を保ったままバグ修正・軽微な変更をしたとき
- 上位の桁が上がったら、下位の桁は0に戻す（例: 1.2.3 → MAJOR増分 → 2.0.0）

`0.y.z`（メジャーが0）は「まだ安定版でない」扱い。互換性を壊す変更をしてもMAJORは上げず、
MINOR/PATCHの運用は開発者の裁量に委ねられる。安定版として運用を始める時点で`1.0.0`にする。

**プレリリース**: `1.2.0-beta.1` のようにハイフンの後に半角英数（ドット区切りで複数可）。
数値のみのフィールドはゼロ埋め不可。プレリリース版は同じ番号の正式版より小さいとみなす。

**ビルドメタデータ**: `1.2.0+build.5` のようにプラスの後に付与。数値のみでもゼロ埋め可。
バージョン比較では**無視**される（ソートや同一判定に影響しない）。

## Conventional Commits の type との対応

変更の種類をConventional Commitsのtypeで分類すると、SemVer増分がそのまま決まる。

| type | 意味 | SemVer増分 |
|---|---|---|
| `feat` | 機能追加 | MINOR |
| `fix` | バグ修正 | PATCH |
| `docs` `style` `refactor` `test` `build` `ci` `chore` | 実装以外・挙動に影響しない変更 | PATCH |
| 上記いずれか＋末尾`!`、または本文に `BREAKING CHANGE:` | 後方互換性のない変更 | MAJOR |

commit名としてそのまま使う場合は `<type>: <説明>`（コロン+半角スペース）の形式にする。
ディレクトリ名等ファイルシステム上の識別子に使う場合はコロンが使えないため、
`<type>-<説明>`（ハイフン区切り）のスラッグ形式に変換する。

## 判断に迷うとき

- 後方互換性を壊すかどうか自信が持てない場合は、**MAJOR側に倒す**（過小評価より過大評価の方が安全）。
- `0.y.z` の段階なら、大きな変更でもMAJORを上げる必要はない（まだ安定版ではないため）。
- 着手時点では影響範囲が確定しないことが多い。暫定でPATCH/MINORを仮置きし、
  実際の差分が固まった時点（マージ・リリース確定時）で見直す運用でよい。
  ただし確定後にバージョン番号を含む識別子（ディレクトリ名・タグ名等）を変更する場合は、
  その識別子への既存の相互参照（他ドキュメントからのリンク・パス記述）を
  全文検索して更新すること。番号を含む識別子は変更コストが高い。
