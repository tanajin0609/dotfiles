# github-conventions — worktree/ブランチ/コミット/PR運用ルール

## なぜ必要か

作業中は「群B」「M1」のような呼び名がその場では便利で、セッション内の会話では自然に
出てくる。しかしこれをそのままworktree名やPRタイトルに使うと、GitHub上のブランチ一覧や
PR一覧を見た別の人（あるいは後日の自分）には意味が伝わらない。命名を決める時点で
「このセッションの文脈を知らない人が読んでも分かるか」を自問する。

## worktree名・ブランチ名

テンプレート: `<repo>/<type>-<slug>`

- `<repo>`: 対象リポジトリ名（EnterWorktreeでは自動的にブランチ名のprefixになるため、
  意識せず`<type>-<slug>`部分だけを`name`引数に渡してよい場合も多い。ツールの挙動に従う）
- `<type>`: Conventional Commitsのtype（`feat`/`fix`/`chore`/`docs`/`refactor`/`test`等）
- `<slug>`: 内容が一目で伝わる短い説明（英語、ハイフン区切り）。セッション内だけの
  呼び名（作業コードネーム、マイルストーンID、Notionのページ名の略称等）は避け、
  「何を変更するか」を直接書く

EnterWorktreeツールの制約（`/`区切りの各セグメントは英数字・ドット・アンダースコア・
ダッシュのみ、全体で64文字以内）を守ること。

**自己チェック**: 名付けたら「このブランチ名だけを見て、事情を知らないメンバーが
変更内容を推測できるか？」を自問する。Noなら書き直す。

### 例

| 良くない例 | 理由 | 良い例 |
|---|---|---|
| `group-b-impl` | 「群B」がセッション内でしか通じない | `feat-input-validation` |
| `m1-work` | マイルストーンIDは外部に意味を持たない | `feat-schema-driven-layers` |
| `fix-stuff` | 何を直すのか分からない | `fix-diff-key-order-mismatch` |

複数の独立した変更を1つのworktreeにまとめる場合は、最も代表的な変更、または
まとめた変更の性質（例: レビュー指摘の一括対応なら`fix-review-followups`）で名付ける。

## ブランチを分けるか、1本にまとめるか

複数の変更を作業するとき、ブランチを分けるべきか1本にまとめるべきか迷ったら、
ファイルの重なりを基準にする。

- **同じファイルを複数の変更が触る、または実装に依存順序がある** → 1本のブランチ・PR
  にまとめる方が安全。別ブランチに分けると、後からマージする側で同じ箇所のコンフリクト・
  手戻りが起きる。
- **互いに独立していてファイルが重ならない** → 別ブランチに分ける方がレビュー・
  取り消し（1件だけrevertする等）がしやすい。

迷ったら「後から分離できるか」で考える。複数の変更が同じファイルに積み重なった状態
から後で分離するのは、diffをhunk単位で手分けする必要がありミスの元になる。着手前に
判断する方が安い。

## コミット粒度

- 複数の変更が同じファイルに積み重なる場合は、最初から1コミットにまとめる。
  後から`git add -p`等でhunk単位に分離しようとすると、変更同士が絡み合っている
  ケースでミスしやすい。
- 互いに独立した変更（ファイルが重ならない）なら、それぞれ別コミットにする方が
  履歴として追いやすく、後から特定の変更だけをrevertしやすい。

## pushする前のセルフチェック

- pushの前に、軽い読み取り系コマンド（`git ls-remote origin`等）で認証が通るか
  確認する。`credential.helper`が未設定だと、対話的な認証入力を待ってハングする
  ことがあり、非対話環境（エージェント実行時等）では気づきにくい。長時間応答が
  無ければ認証設定を疑う。
- mainブランチへの直接push・force pushは絶対にしない。
- pushする対象ブランチが意図したworktreeのものか確認する。複数worktreeを並行
  させているときは、誤って別のworktreeのブランチをpushしないよう
  `git branch --show-current`等で確認してから実行する。

## PRのタイトル・本文

- **タイトル**: worktree名の`<type>-<slug>`部分と一貫させる（例: worktreeが
  `feat-input-validation`なら、タイトルは`feat: クライアント側の必須項目チェックを追加`
  のように対応させる）。70文字以内。
- **本文**: SummaryとTest planの2セクション構成を基本とする（詳細な書式は
  プロジェクトのPR作成ルールに従う）。

複数の独立した変更（例: 複数の`docs/changes/`配下のchangeや、レビュー指摘の複数項目）を
1つのPRにまとめる場合、Summaryで「どの変更が何を含むか」を項目ごとに列挙する。読み手が
「このPRは1つのまとまった変更」なのか「複数の独立した変更の束」なのかを一目で判別できる
ようにするため。

```markdown
## Summary
このPRには以下の独立した変更が含まれる:
- **feat-input-validation**: クライアント側の必須項目チェックを追加
- **chore-adversarial-tests**: 異常系入力のテストを追加

## Test plan
- [ ] 検証項目1
- [ ] 検証項目2
```

単一の変更だけをまとめたPRでは、この列挙は不要（通常のSummary箇条書きで足りる）。

## PRのライフサイクル

draft PRで作成するか最初からreadyにするか、マージ方式（squash/rebase/merge commit）
はプロジェクトごとに慣習が違うため、ここでは断定しない。プロジェクトの
`CONTRIBUTING.md`や過去のPR履歴を確認し、不明ならユーザーに確認する。
