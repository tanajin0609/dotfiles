# security-by-design

後付け対策は下流ほど是正コストが増える。だから設計段階で入れる。ただし基準を100%満たそうとして
チームを疲弊させない。**対象のリスクに見合う最小限の対策を、今回の変更範囲で入れる**のが判断軸。
原則・用語・チェック項目の詳細は `references/principles.md` を参照する。

## モード選択

| 状況 | モード |
|---|---|
| 新機能・改修の設計を書いている（コード未着手） | A |
| 書き上がった設計書／コード差分がある | B |
| 既存システムの改修で、全面対応は無理だが何か入れたい | C |

複数該当する場合は A→B の順に続けて実施してよい。対象が判別できなければ AskUserQuestion で聞く。

## A. 設計時の脅威モデリング

1. 変更対象のデータフロー（入力元→処理→保存先→出力先）と信頼境界を列挙する。
2. 信頼境界をまたぐ箇所ごとに STRIDE（なりすまし・改ざん・否認・情報漏えい・DoS・権限昇格）で脅威を挙げる。
   該当しない分類は書かない。
3. 各脅威に「影響×起こりやすさ」で高/中/低を付け、高・中にだけ対策を割り当てる。低はリスク受容として1行残す。
4. components.md に「セキュリティ」節として 脅威×対策×採否 の表を書く。デフォルト設定
   （初期値・権限・ログ有効化）を明記する。

## B. 設計・差分レビュー

`references/principles.md` の「レビュー観点」を上から確認する。変更に無関係な観点は飛ばす。
指摘は ReportFindings で報告する（`category` は `security`）。「この設計でどう攻撃されるか」を
`failure_scenario` に具体的に書き、一般論の指摘は出さない。

## C. 既存システムの段階適用

全面改修は提案しない。今回触るモジュールに限って、次の順に候補を挙げる:
1. 改修箇所の入力検証の厳格化・認可チェックの追加（コード変更のみで済む）
2. 改修画面/APIへの MFA・ログ出力の追加
3. 依存関係の可視化（SCA・SBOM）や境界防御（WAF/APIゲートウェイ）— インフラ変更を伴うので提案に留める

各候補に「工数感」と「防げる攻撃」を添え、採否はユーザーに委ねる。新しいツール・依存の導入は確認を取る。

## 共通の注意

- 認証・暗号は独自実装を提案しない。実績あるライブラリ/フレームワーク機能を使う。
- 対策を採らない判断も正当。その場合は理由を残させる（リスク受容の明示）。
