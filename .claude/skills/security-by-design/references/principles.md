# セキュリティ・バイ・デザイン 原則と観点

出典: https://qiita.com/HIsui0921/items/49cbb1eaead2dcde4bd4 （CISA "Secure by Design" ほかを整理した記事）

## CISA 3原則

1. **責任の所有** — SSO・MFA・セキュリティログを有料オプションにせず基本機能にする。脆弱性クラスごと消す
   （メモリ安全言語、堅牢化）。出荷状態が最も安全な状態（Secure by Default）。
2. **透明性と説明責任** — MFA利用率・パッチ適用速度などを開示。脆弱性は CWE ベースで根本原因分析（RCA）。SBOM提供。
3. **リーダーシップ** — 統括責任者を決め、セキュリティ指標を経営に定期報告する。

## レビュー観点

### デフォルト設定
- 共通の初期パスワードが無いか（個体別、または初回変更強制）
- 特権アカウントに MFA が既定で強制されるか
- セキュリティログが既定で有効か（誰が・いつ・何をしたか追えるか）
- 古いプロトコル・弱い暗号方式が無効化されているか
- 権限・公開範囲の初期値が最小か

### 入力と境界
- 信頼境界をまたぐ入力すべてに検証があるか（SQLi・XSS・パストラバーサル等）
- 認可チェックがサーバ側で毎リクエスト行われるか
- エラー応答・ログに秘密情報や個人情報が出ていないか

### 認証・暗号
- 独自実装していないか（OWASP Top 10 Proactive Controls 準拠のライブラリ利用）
- 秘密情報がコード・リポジトリに埋め込まれていないか

### 依存関係・供給網
- 新規依存の妥当性、既知脆弱性（SCA）
- SBOM を生成・管理できる状態か

### 開発プロセス（組織/リポジトリ単位の評価時のみ）
- 企画段階の脅威モデリング（STRIDE / PASTA）の有無
- CI/CD のガードレール（SAST・SCA・DAST・コンテナスキャン）
- KPI: 脆弱性 MTTR、リリース前未解決件数、MFA 適用率
- セキュリティチャンピオンの配置、NIST SSDF（SP 800-218）準拠

## 既存システムへの段階適用
- 境界防御: WAF / API ゲートウェイで外側から遮断
- 改修時の部分適用: 触るモジュールだけ MFA 必須化・入力検証強化
- 可視化: SCA で依存と SBOM を把握し、脆弱性の影響範囲を即特定
- 既存フレームワーク活用: 認証・暗号は実績あるライブラリへ

## 用語
- STRIDE: Spoofing / Tampering / Repudiation / Information disclosure / Denial of service / Elevation of privilege
- PASTA: リスク中心の7段階脅威モデリング手法
- NIST SSDF: セキュア開発フレームワーク（SP 800-218）
- S-SDLC: セキュア開発ライフサイクル
