# テスト・リリース・運営

## 確認の4層

下の層ほど速く回せる。Claudeが担当できるのは1〜3、4は人にしかできない。

| 層 | 何を確かめるか | 誰が | 方法 |
|---|---|---|---|
| 1. ロジックの単体テスト | ダメージ計算、当たり判定、進行条件、セーブの読み書き | Claude | 描画なしで関数を呼ぶ。乱数は種を固定 |
| 2. 自動プレイ | 止まらない・落ちない・進行不能にならない | Claude | 入力を機械的に流して数千フレーム進め、例外と異常値（画面外、体力が負）を検出 |
| 3. 起動確認 | 実際に画面が出る、主要場面が崩れていない | Claude | 画面なしモードやブラウザ自動操作で起動し、スクリーンショットとエラーログを見る |
| 4. プレイテスト | 面白いか、分かるか、難しすぎないか | 人 | 実際に遊ぶ |

1〜3が通っても「面白い」は保証されない。報告では4が未実施であることを明示する。

## プレイテストの取り方

作った本人は操作もルールも知っているため、分かりにくさに気づけない。初見の人に頼めるなら次を守る。

- **説明しない・助けない**。詰まった場所がそのまま改善点になる。
- 感想より**行動**を記録する: どこで止まったか、何回やられたか、どこでやめたか、何を読み飛ばしたか。
- 「どうすれば良くなるか」は聞かない。「何が起きたと思ったか」「何をしようとしたか」を聞く。
- 1回のテストで直す問題は上位3つまで。直したら別の初見の人で試す。

Claudeへの依頼に変えるときは「難しい」ではなく「2面の3つ目の足場で5回中4回落ちた」の形で伝えてもらう。

## バランス調整

- 目標を数字で置く（例: 1面の初回クリア率、1プレイの長さ、ボスの想定挑戦回数）。
- 変更は1回に1項目、幅は大きく（±20〜50%）。小刻みに変えると違いが体感できない。
- 自動プレイで取れる数字（平均生存時間、武器ごとの使用率・撃破数）は、極端な偏りの検出に使う。面白さの代わりにはならない。
- 上手い人と初めての人で必要な難易度が違う。1本の調整で両立しないなら、難易度選択や救済（連続失敗で易しくなる）を検討する。

## バグの記録

```
再現手順: 起動から何をしたか（番号つき）
期待: こうなるはず
実際: こうなった
環境: 機種/OS/ビルド番号、乱数の種（あれば）
頻度: 毎回 / 時々（n回中m回）
```

優先度は「進行不能・データ消失」＞「頻繁に起きる不具合」＞「見た目の乱れ」＞「まれな不具合」。

## 公開前チェック

- [ ] 最初から最後まで、公開用ビルドで通しプレイした（開発用ビルドではなく）
- [ ] 開発用の機能（無敵・ステージ選択・デバッグ表示）が無効になっている
- [ ] 最低動作環境で目標フレームレートが出る
- [ ] セーブ → 終了 → 再開が正しく動く。壊れたセーブデータで起動不能にならない
- [ ] ウィンドウサイズ変更・全画面切替・フォーカス喪失（別ウィンドウに切替）で壊れない
- [ ] 音量設定と操作設定が保存される
- [ ] 素材のクレジット一覧とライセンス条件を満たしている
- [ ] 公開先の必須項目（説明文、スクリーンショット、年齢区分、個人情報の扱いの申告など）を用意した
- [ ] クラッシュや不具合の報告を受け取る窓口がある

## 公開先

| 公開先 | 特徴 | 向く段階 |
|---|---|---|
| ブラウザ公開（自前ホスティングや投稿サイト） | 導入不要で遊んでもらえる。審査が軽い/無い | 試作の公開、反応を見る |
| PC向けストア | 利用者が多い。登録料・審査・ストアページ準備が要る | 完成品の販売 |
| スマホ向けストア | 開発者登録・審査・規約順守（課金、広告、個人情報）が要る | スマホ前提の設計の作品 |
| 家庭用ゲーム機 | 事業者としての契約と専用の開発環境が要る | 実績ができてから |

登録料・手数料・審査基準は変わるため、公開を決めた時点で公式情報を確認する。Claudeはストアへの申請操作そのものは行わず、提出物の準備と確認リストの作成までを担当する。

## 伝え方（宣伝）

- 1文コンセプト（→ `design.md`）をそのまま紹介文の1行目に使えるか確認する。使えないなら、コンセプトが曖昧。
- 最初の数秒で遊びが分かる動画/GIFが最も効く。タイトルロゴから始めない。
- 完成してから告知するのではなく、開発中から見せて反応を集める。反応が薄いこと自体が企画への情報になる。

## 公開後

- 公開直後は不具合報告が集中する。修正版を出せる手順（ビルド → 更新の配信）を公開前に一度通しておく。
- 更新でセーブデータを壊さない（バージョン番号で読み替える → `implementation.md`）。
- 要望は件数だけで判断しない。「何に困っているか」に戻して、コアループを強める変更を優先する。
- 利用状況を収集する場合は、収集する項目と目的を明示し、公開先と地域の個人情報ルールに従う。
