# game-dev

Claudeはゲームを実装できるが、**面白いかどうかは体感できない**。面白さの判定は人がプレイして行う。
このskillの目的は「人が触って判定する」までの時間を最短にし、判定結果を次の変更に確実に反映すること。

例: 料理人（Claude）は味見ができない。だから一皿を小さく早く出し、客（ユーザー）の一口ごとの感想で味を直す。フルコースを作り切ってから初めて味見してもらう進め方は取らない。

## 原則

1. **コアループを最初に動かす**。タイトル画面・セーブ・設定・演出より先に、プレイヤーが数秒〜数十秒ごとに繰り返す操作（例: 狙う→撃つ→当たる→スコア）を触れる状態にする。
2. **1回の依頼で検証する仮説は1つ**。「ジャンプの手触り」と「敵の配置」を同時に変えると、どちらが効いたか人が判定できない。
3. **調整値はコードに埋めない**。速度・重力・ダメージ・出現間隔は1か所（設定ファイルや定数テーブル）に集め、人が数値だけ変えて試せるようにする。
4. **Claudeが確認できたことと、人にしか確認できないことを分けて報告する**。起動する・クラッシュしない・ロジックのテストが通る、は前者。手触り・難易度・見た目の良さは後者。
5. **スコープは削る方向に倒す**。機能を足す提案より、完成に不要なものを外す提案を優先する。
6. **既存作品の再現はしない**。ジャンルやメカニクスは参考にしてよいが、固有の名称・キャラクター・素材・レベル構成は写さない。

## 工程と役割分担

| 工程 | この工程のゴール | Claudeがやる | 人がやる | 次へ進む条件 |
|---|---|---|---|---|
| 1. 企画 | 1文コンセプトとコアループが決まる | 案の言語化、スコープの切り出し、検証する仮説の列挙 | 何を作りたいかの決定 | 「誰が・何をして・何が気持ちいいか」を1文で言える |
| 2. プロトタイプ | コアループの面白さを判定する | 仮素材（四角形・無音可）で最短実装 | プレイして判定 | 人が「もう1回やりたい」と言う。言わなければ1に戻る |
| 3. 基本設計 | 作る範囲と構造が決まる | エンジン・構成・データ形式の提案、作るものリスト | 範囲の承認 | 作らないものリストが合意されている |
| 4. アルファ | 最初から最後まで通して遊べる | 主要システムの実装、ロジックの自動テスト | 通しプレイ | 仮素材のままエンディング（または1周）まで到達できる |
| 5. ベータ | 内容が出揃う | 全ステージ・UI・音・演出の実装 | 素材の選定、プレイテスト | 新機能の追加を止められる（以降は修正と調整のみ） |
| 6. マスター | 公開できる品質になる | バグ修正、性能計測、ビルド、公開チェック | バランス最終判断、公開操作 | 公開チェックリストが全て埋まる |

プロトタイプのコードは捨てる前提で書く。4に進むとき、作り直すか流用するかを人に確認する。

## 実装後の報告形式

```
変更: 何を変えたか（検証したい仮説を1行で）
確認済み: Claudeが実行して確かめたこと（起動・テスト結果・スクリーンショット）
触って見てほしい点: 人にしか判定できないこと（最大3つ、操作手順つき）
調整つまみ: 数値名と場所、現在値、上げ下げするとどうなるか
```

## このskillの根拠について

内容はゲーム開発で広く知られた実務知識をまとめたもので、個別の出典は検証していない。エンジンやストアの仕様・規約・料金は変わるため、該当箇所は作業時に公式情報で確認する。
