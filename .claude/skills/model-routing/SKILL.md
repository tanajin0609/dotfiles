# model-routing

モデルは「重要そうだから強いモデル」ではなく、**タスクの構造**で選ぶ。判断に迷ったら下げない — ダウングレードで質が落ちて手戻りになるコストは、節約できるコストより大きいことが多い。

## 判断軸

タスクを次の2軸で見る。

1. **事実の列挙・検索** か、**判断・統合・創作** か
   - 前者（ファイル特定、grep、ログの一次スクリーニング、定型変換）は弱いモデルでも精度が落ちにくい
   - 後者（設計判断、曖昧な要件の解釈、複数の情報源の統合、レビュー）は弱いモデルだと質が落ちやすい

2. **誤りが後工程で検出可能か**、それとも**誤りがそのまま資産になるか**
   - テストやユーザー確認が必ず入る一次ドラフトは、外れても直せる
   - 一発勝負で後戻りコストが高い変更（本番影響、他者への回答、削除的操作）は検出網が薄いので質を優先する

## サブエージェント (Agent tool) のmodel選択

- 単純なファイル特定・キーワード探索（Explore的、read-only）で、prompt文で指示する探索範囲が「quick」「medium」相当（`breadth`はAgent toolの正式パラメータではなく、prompt文への自己申告に過ぎない点に注意）なら、`model: "haiku"` を明示指定してよい。
- 「very thorough」（多数の場所・命名規則をまたいで網羅する）を指示する場面は、網羅性そのものを要求している以上haikuは避け、エージェント既定モデルのままにする。
- 大量ログ/diff/出力の一次要約（ノイズ除去が目的で、後で自分が精査する前提）も `haiku` でよい。
- 探索結果から設計判断や複数解釈の絞り込みまで期待する調査、コードレビュー、計画立案は、エージェント定義の既定モデル（通常sonnet相当）のままにする。安易にhaikuへ倒さない。
- 並列に多数投げて個々の精度要求が低い調査（同じパターンを多ファイルに探すだけ等）は、haiku化するとコストが並列数に比例して効いてくるので優先的に検討する（件数のしきい値は明文化しない。個々の判断に委ねる）。

## メイン対話のモデル切り替え

- 既定モデル（多くの環境ではsonnet）を動かすのは例外的な場面だけにする。
- **上げる場面**: 曖昧な要件の解釈、アーキテクチャ判断、セキュリティ/本番影響のある変更、他者のコード・設計のレビューで、かつ「既定モデルでは何が具体的に不足か」を一言で言えるとき。言えなければ既定モデルで始め、同じ論点で2〜3回詰まった時点でその場で昇格する。
- **重要性と難度は別物**: 「誤ると被害が大きい／一発勝負で後戻りコストが高い」ことは、それ単独では格上げの根拠にならない。被害の大きさへの対策はテスト・人間レビュー・承認ゲート・機械チェック（grep等）といった工程側のゲートで吸収し、モデル選択は「そのモデルが実際にその判断をこなせるか」だけで決める。
- **下げる場面**: 定型的な繰り返し作業（命名の一括変換、フォーマット整形、単純な集計・抽出）が連続するとき。人間の意思決定や解釈が絡む判断は含めない。
- `/fast` はモデルのダウングレードではなく応答速度の優先であることに注意する（Opus系での高速出力）。

## アンチパターン

- 「重要そうだから」で毎回強いモデルにする → 単純作業まで巻き込まれてコストだけ増える
- 「重要そうだから」を「一発勝負で後戻りコストが高いから」と言い換えて格上げする → 影響度を難度の代理指標にしている。既定モデルが実際にその判断を誤る根拠を示せないなら、工程側のゲートで被害を吸収できないか先に検討する
- 「探索だから」で毎回弱いモデルにする → 探索の中に依存関係の解釈や曖昧な命名からの意図推定が混ざっている場合、精度が落ちる
- モデルを下げた後、出力が期待と違うと感じても気づかず/無視して進める → 一度でも「怪しい」と思ったら、同タスクを1段階上のモデルで再実行するコストを厭わない。下げた後の検証を省略しない（サブエージェント呼び出しでは呼び出し側が、ユーザーが手動切替した低モデルの対話では低モデル自身も対象）。ただし低能力モデルほど自身の限界を認識しにくい傾向があるため、「怪しい」の閾値は低めに（迷ったら申告する）設定する。

## モデル選択以外のトークン節約

モデルを下げること以外にも、メインの対話コンテキストを汚さない手段がある。

- ノイズの多い調査（grepの束、ログの束、多数ファイルの一括確認）はサブエージェントに投げて、要約だけを持ち帰る。
- 読んだファイルを不必要に再読しない。Edit/Writeは失敗時にエラーを返すので、成功したことが分かっている変更を確認のためだけに読み直さない。
- 同じ情報を得るための往復（確認質問の連投）をまとめる。分かっている前提を都度聞き直さない。

## 適用チェックリスト

タスクに着手する前に自問する。

- [ ] これは「列挙・検索」か「判断・統合」か
- [ ] 誤りは後工程で検出されるか、そのまま資産になるか
- [ ] 失敗時の再実行コストは低いか
- [ ] （サブエージェントの場合）この呼び出しは並列で多数飛ぶか、精度要求はどの程度か
- [ ] （サブエージェントの場合）探索範囲を「very thorough」で指示するなら、haikuを避けたか
