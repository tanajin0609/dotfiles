# uiux-review

評価軸は2ファイルに分かれている。

- `references/uiux-heuristics.md` — 根拠側。「なぜそう判断するのか」（原則の説明、NG例/OK例）
- `references/uiux-checklist.yaml` — 実行側。「何を見るか」（id・category・requires・auto・severityを持つ機械可読なチェック項目一覧）

本ファイルは実行手順と出力フォーマットのみを扱う。個々の判定基準は都度チェックリストを引き、その根拠・NG例/OK例が欲しい場合のみheuristics.mdの該当章を読む。`ref` を持たない項目はheuristics.mdに対応する章が無い場合がある。そのときは `check`/`rule` 本文を根拠として扱い、原則名を捏造しない。

深刻度・確信度・出力仕様・運用ルールの定義は `uiux-checklist.yaml` を単一の正とする（本ファイルは実行に必要な範囲だけを再掲する）。

## 実行手順

**読み込みと書き出しは最小回数で行う。** 最初の1ターンで、次の Read を**並列に同時に**呼ぶ: `references/uiux-checklist.yaml` を offset=1/limit=800 と offset=801/limit=800 の2分割、およびレビュー対象の入力。Bash の `cat` は出力上限で切れて再読込が発生するので使わない。heuristics.md は判定に不可欠な章がある場合だけ読む。結果は次のターンで1回で書き出す（ツール呼び出しのたびに会話全体が再読み込みされ、消費が回数に比例するため）。

0. **目的とシナリオを確定する**。対象画面・機能の目的（誰が・何をするためのものか）と、ゴールまでの主要シナリオ（1〜3本。例: 初回に予約して完了するまで）を決める。
   - spec・README・画面の文言から推定できればそれを採用し、サマリに「前提とした目的」として1行書く。推定できなければ最も妥当な目的を仮置きして続行し、その仮定を要確認の先頭に質問形式で出す（fork実行のためユーザーへ質問できない）。
   - 目的が確定しない、または依頼がアクセシビリティ等の観点に限定されている場合は、手順1.5を飛ばしてその旨をサマリに1行書く。

1. **入力の種類を列挙する**。今回の入力が `code` / `screenshot` / `flow` / `runtime` のどれに当たるかを挙げる。複数該当しうる（コードとスクリーンショットが同時にあるのが最も多い）。
   - 入力が添付されていない場合は、ここで止まって入力を求める。一般論を語らない。
   - `runtime` を要求する項目があり、かつ起動可能なアプリが手元にある場合は、実際に操作して `runtime` を取得してから判定する（要確認に落とさない）。
   - ワイヤーフレームの場合は、視覚表現がまだ決まっていない項目（`A11Y-P-02` `A11Y-P-03` `GST-02` `TOKEN-01` `TOKEN-04` `THEME-*`）を対象外にする。
1.2. **実測する**（`runtime` としてURLで開けるページがあるときだけ）。このSKILL.mdと同じディレクトリの `scripts/a11y-audit.sh <URL> /tmp/uiux-review-audit` を Bash で実行し、`/tmp/uiux-review-audit/axe.json` と `lighthouse-summary.json` を読む（axe-core 4.14.1 と Lighthouse 13.6.0 のアクセシビリティ監査。どちらも npm から `/tmp` に取得し、対象リポジトリの依存には加えない）。
   - 違反（axe の `violations`、Lighthouse の `failed`）は、下表のidの指摘として確信度「確定」で出し、根拠にルールidと対象セレクタ・測定値（コントラスト比など）を書く。両ツールが同じルールidで違反を出したら1件にまとめる。
   - 表に無いルールの違反は `[axe: <rule id>]` として出す。深刻度は axe の impact で決める（critical=高 / serious=中 / moderate・minor=低）。
   - 違反が無いことを「問題なし」の根拠にしない。axe-core は適合率0.90に対し再現率0.36（arXiv 2609.09379）、自動検出できるのは件数で57%（Deque）なので、手順2・6は実測後も省かない。axe の `incomplete` は要確認に回す。
   - フォーカス管理・キーボードトラップ（`A11Y-O-04`）・読み上げ順と視覚順の一致（`A11Y-O-03`）は自動ツールで判定できない。Playwright でキーボード操作して確かめられれば判定し、できなければ要確認に出す。
   - スクリプトが失敗した（ネットワーク不可・ページを開けない）ときは手順6の表だけで判定し、サマリに「実測できず（理由）、機械チェック表で判定」と1行書く。

   | axe / Lighthouse のルールid | チェックリストid |
   |---|---|
   | `image-alt` `input-image-alt` `role-img-alt` `svg-img-alt` `area-alt` | `A11Y-P-01` |
   | `color-contrast` | `A11Y-P-02` |
   | `html-has-lang` `html-lang-valid` | `A11Y-U-01` |
   | `label` `select-name` `aria-input-field-name` | `A11Y-U-02` |
   | `tabindex` | `A11Y-O-03` |
   | `target-size` | `A11Y-O-06` |
   | `bypass` | `A11Y-O-10` |
   | `heading-order` | `A11Y-R-01` |
   | `meta-viewport` | `MOB-06` |
   | `autocomplete-valid` | `FORM-03` |
   | `th-has-data-cells` `td-headers-attr` `scope-attr-valid` | `TABLE-01` |

   `label` が通っても、プレースホルダーだけの入力欄は `FORM-01`（常時可視のラベル）として別に判定する（axe はプレースホルダーをアクセシブルな名前として認める）。
1.5. **シナリオをウォークスルーする**。チェックリスト走査より先に、手順0のシナリオをステップ（画面・セクション）ごとに辿り、`category: walkthrough` の4問（`WALK-01`〜`04`）に答える。根拠は `uiux-heuristics.md` の23章。
   - 起動可能なアプリがあれば実際に操作して辿る（確信度「確定」可）。無ければルーティング・画面・遷移図から推定し、確信度は「推定」以下にする。
   - 詰まった箇所は `WALK-*` のidで指摘に含める。同じ事象を既存項目（`IA-02` 等）でも出さない。
2. **チェックリストを引く**。`uiux-checklist.yaml` の `items` を `category` 単位で走査する。`requires` は OR なので、**いずれか1つでも手元にあれば判定を試みる**。全部揃っている場合のみ確信度を「確定」にでき、一部しか無ければ「推定」以下に落とす。判定を試みずに「要確認」（質問形式）へ回すのは `requires` のいずれも無い項目だけ。
   - `walkthrough` は手順1.5で扱ったので、ここでは走査しない。
   - 後半の `category`（`ethics` / `mobile` / `performance` / `ia` / `onboarding` / `i18n` / `design_system` / `privacy` / `consistency` / `platform`）は見落としやすい。ここまで到達したことを必ず確認する。
   - `auto` フィールドは確信度の根拠にしない。実測結果を確信度に使うのは手順1.2の表にあるidだけ。
3. **条件付きカテゴリの要否を決める**。`theme`（ダークテーマ等の複数テーマがある）、`notification`（通知・トーストがある）、`table`（データ表・一覧がある）、`dataviz`（グラフがある）、`ai`（AI生成・AIとの対話がある）は、該当する要素が入力に無ければ走査せず、対象外とした旨をサマリに1行で書く。チェックリストに無い観点を指摘する場合のみ `[narrative: 原則名]` を使う。
4. **良い点は指摘が3件以上あるときのみ1〜2件挙げる**。指摘だけに偏ると改善の方向を誤らせるため。無ければ省略してよく、無理に捻り出さない。
5. **件数より優先度**を意識する。低深刻度の指摘を大量に出すより、高深刻度を絞って出す方が価値がある（目安: 高3件、低は20件も出さない）。`note` に「片方のみ出す」とある重複ペアは、同じ事象から2件出さない。
6. **機械チェックを最後に走査する**。コードがある場合、以下は grep 相当で確実に判定できるうえ見落としやすい。出力を書き終える前に、この表を上から順に必ず確認する。

   | 見るもの | id |
   |---|---|
   | `<html>` に `lang` | `A11Y-U-01` |
   | `<img>` に `alt`（装飾は `alt=""`） | `A11Y-P-01` |
   | 入力欄に `label for` / `aria-label` | `A11Y-U-02` / `FORM-01` |
   | `outline: none` の置き去り | `A11Y-O-02` |
   | 正の `tabindex` | `A11Y-O-03` |
   | 動的更新領域に `aria-live` / `role="status"` / `role="alert"` | `A11Y-R-03` |
   | 繰り返しを飛ばす手段（スキップリンク / ランドマーク / 見出し） | `A11Y-O-10` |
   | `div`/`span` に `onclick` | `A11Y-R-02` |
   | viewport の `user-scalable=no` / `maximum-scale` | `MOB-06` |
   | 入力欄の `type` / `inputmode` / `autocomplete` | `FORM-02` / `FORM-03` |
   | チェックボックスの `checked` 初期値 | `DARK-01` |
   | `:hover` でしか出ない情報 | `MOB-05` |
   | データ表の `<th>` と `scope` | `TABLE-01` |

   該当が無ければ「問題なし」と判断してよいが、**確認自体を飛ばさない**。手順1.2で実測済みの違反と同じ事象は重ねて出さない。
7. **流行由来のアンチパターンを照合する**。`design-antipatterns` skill の一覧（自動カルーセル、半透明UI、AI生成UI定型など）を検出シグナルと照合し、該当すれば `[AP-xx]` のidで指摘に含める。

## 出力前の自己検証

全手順を終えて書き出す直前に、全指摘を入力へ再照合する。GPT-4o の指摘の24.3%は偽陽性で、原因はハルシネーションと静止画から検出できない操作上の問題の推測だった（arXiv 2506.16345）。AIは検証できない仮定を置き、美観の不一致を強調しやすい（arXiv 2510.17056）。

1. **根拠位置を書けるか**。「根拠」に入力上の位置を書く（コードはファイル名と行番号、スクリーンショットは画面名と領域、実測は手順1.2のルールidとセレクタ、ウォークスルーは表の行番号）。原則名だけでは位置にならない。書けない指摘は要確認へ移し、質問形式に書き直す。
2. **観察できる挙動か**。操作後の挙動（送信後のフィードバック、エラー表示、確認ダイアログ、取り消し手段など）は、それを実装したコード・遷移図、または `runtime` での操作結果があるときだけ指摘にする。静止画や、処理が入力に含まれないコードから推測した挙動は要確認へ移す。
3. **深刻度「高」は消さない**。1・2で移す指摘が「高」なら、要確認の先頭に `[深刻度: 高]` を付けて残す。検証は本物の問題も落としうるため。
4. **同一原因は1件にまとめる**。同じ要素・同じ原因から複数idが出ていれば、深刻度の最も高いidに寄せ、他のidは根拠に併記する。
5. **見た目だけの指摘は「低」まで**。タスクの完了・誤操作・アクセシビリティに影響せず、見た目の好みや統一感だけを問う指摘は深刻度を「低」にする（コントラスト・タップ領域は該当しない）。

## 出力フォーマット

出力全体は次の順で構成する（`uiux-checklist.yaml` の `output_structure`）。

1. サマリ（3行以内。前提とした目的、高が何件か、最優先の1件は何か）
2. シナリオ別ウォークスルー表（手順1.5を実施したときのみ）
3. 深刻度: 高 → 中 → 低 の順。`category` 順・id順にはしない
4. 要確認（別枠。質問形式。自己検証で移した深刻度「高」は先頭に `[深刻度: 高]` を付けて残す）
5. 良い点（手順4の条件を満たすときのみ。深刻度・確信度は付けない）

指摘が0件の場合は「指摘なし」と明記し、代わりに要確認を厚く出す。

ウォークスルー表は1シナリオ1表で、各列は○/△/×で埋める（`uiux-checklist.yaml` の `walkthrough_format`）。

```
シナリオ: <ゴール>
| # | 画面・セクション | ユーザーの意図 | 何をする画面か(WALK-01) | 次の操作(WALK-02) | ゴールとの対応(WALK-03) | 進捗の手応え(WALK-04) | 詰まる点 → 指摘id |
```

指摘は1件ずつ以下の形式で出す（`uiux-checklist.yaml` の `output_format`）。`id` はチェックリストにある項目ならそのid（例: `A11Y-P-01`）、チェックリストに無いnarrative項目は `[narrative: 原則名]` と書いてidと区別する。

```
[深刻度: 高/中/低] [確信度: 確定/推定/要確認] [id] 対象箇所
  問題: 何が起きているか
  根拠: どの入力から判断したか（該当コード行 / スクショの箇所 / 原則名）
  影響: ユーザーがどう困るか
  改善案: 具体的な変更内容
```

yaml の英語キーは出力時に日本語へ置き換える（`high`=高 / `medium`=中 / `low`=低、`confirmed`=確定 / `inferred`=推定 / `needs_check`=要確認）。深刻度・確信度の判定基準は `uiux-checklist.yaml` の `enums` を参照する。

推測を事実として断定しない。「〜のはずです」ではなく「〜か確認してください」と書く。コントラスト比を書くときは実際に計算し、採用した前景色・背景色・文字サイズを併記する。AAA の達成基準は、AA 適合を目標とする案件では「違反」と書かず推奨として出す。
