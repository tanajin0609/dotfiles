# uiux-review

評価軸は2ファイルに分かれている。

- `references/uiux-heuristics.md` — 根拠側。「なぜそう判断するのか」（原則の説明、NG例/OK例）
- `references/uiux-checklist.yaml` — 実行側。「何を見るか」（id・category・requires・auto・severityを持つ機械可読なチェック項目一覧）

本ファイルは実行手順と出力フォーマットのみを扱う。個々の判定基準は都度チェックリストを引き、その根拠・NG例/OK例が欲しい場合のみheuristics.mdの該当章を読む。

## 実行手順

1. **入力の種類を確認する**。今回の入力が `code` / `screenshot` / `flow` / `runtime` のどれに当たるかを特定する（`uiux-heuristics.md` の「0. 入力の種類と判定できる範囲」も参照）。
2. **チェックリストを引く**。`uiux-checklist.yaml` の `items` を上から見て、各項目の `requires` が手元の入力でカバーされているものだけを判定対象にする。カバーされていない項目は判定せず、`confidence: needs_check` として指摘ではなく質問形式で出す（`review_rules` 参照）。
3. **narrative項目を補う**。プラットフォームガイドライン（HIG/Material）や多言語対応など、チェックリストにid化されていない観点は `uiux-heuristics.md` 本文（11章・15章・17章など）から拾う。
4. **良い点も1〜2件挙げる**。指摘だけに偏ると改善の方向を誤らせる。
5. **件数より優先度**を意識する。低深刻度の指摘を大量に出すより、高深刻度を絞って出す方が価値がある。

## 出力フォーマット

指摘は1件ずつ以下の形式で出す（`uiux-checklist.yaml` の `output_format` と同一）。`id` はチェックリストにある項目ならそのid（例: `A11Y-P-01`）、チェックリストに無いnarrative項目なら原則名をそのまま書く。

```
[深刻度: 高/中/低] [確信度: 確定/推定/要確認] [id] 対象箇所
  問題: 何が起きているか
  根拠: どの入力から判断したか（該当コード行 / スクショの箇所 / 原則名）
  影響: ユーザーがどう困るか
  改善案: 具体的な変更内容
```

**確信度**は入力から直接判定できるものだけ「確定」とする。一般論としては妥当だが入力からは断定できないものは「推定」、判定に必要な入力自体が無いものは「要確認」（指摘ではなく質問として出す）。

**深刻度**は「高＝タスクを完了できない／データを失う／法令リスクがある」「中＝完了できるが著しく手間・誤操作を誘発」「低＝完了に支障はないが体験を損なう」の3段階。

推測を事実として断定しない。「〜のはずです」ではなく「〜か確認してください」と書く。
