# uiux-review

UI/UX評価の根拠となる原則・チェック観点は `references/uiux-heuristics.md` にまとめてある。本ファイルは実行手順と出力フォーマットのみを扱う。詳細な原則の説明・NG例/OK例はレビュー中に都度 `references/uiux-heuristics.md` を参照すること（目次から該当章に飛べる）。

## 実行手順

1. **入力の種類を確認する**（`references/uiux-heuristics.md` の「0. 入力の種類と判定できる範囲」）。スクリーンショット1枚しかないのにキーボード操作性やDOM構造を断定しない。判定に必要な入力が無い項目は、指摘ではなく「要確認」として別枠に出す。
2. **該当する評価軸を選ぶ**。単一画面ならニールセン10原則・ゲシュタルト原則・WCAG・フォーム設計・マイクロコピーが中心。複数画面にまたがる依頼（フロー、遷移図）なら「完結感」「エラー復帰導線」「主導権」「ダークパターン」も見る。
3. **良い点も1〜2件挙げる**。指摘だけに偏ると改善の方向を誤らせる。
4. **件数より優先度**を意識する。低深刻度の指摘を大量に出すより、高深刻度を絞って出す方が価値がある。

## 出力フォーマット

指摘は1件ずつ以下の形式で出す。

```
[深刻度: 高/中/低] [確信度: 確定/推定/要確認] [原則: N-x] 対象箇所
  問題: 何が起きているか
  根拠: どの入力から判断したか（該当コード行 / スクショの箇所 / 原則名）
  影響: ユーザーがどう困るか
  改善案: 具体的な変更内容
```

**確信度**は入力から直接判定できるものだけ「確定」とする。一般論としては妥当だが入力からは断定できないものは「推定」、判定に必要な入力自体が無いものは「要確認」（指摘ではなく質問として出す）。

**深刻度**は「高＝タスクを完了できない／データを失う／法令リスクがある」「中＝完了できるが著しく手間・誤操作を誘発」「低＝完了に支障はないが体験を損なう」の3段階。

推測を事実として断定しない。「〜のはずです」ではなく「〜か確認してください」と書く。
