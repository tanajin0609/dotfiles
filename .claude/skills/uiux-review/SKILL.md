# uiux-review

評価軸は2ファイルに分かれている。

- `references/uiux-heuristics.md` — 根拠側。「なぜそう判断するのか」（原則の説明、NG例/OK例）
- `references/uiux-checklist.yaml` — 実行側。「何を見るか」（id・category・requires・auto・severityを持つ機械可読なチェック項目一覧）

本ファイルは実行手順と出力フォーマットのみを扱う。個々の判定基準は都度チェックリストを引き、その根拠・NG例/OK例が欲しい場合のみheuristics.mdの該当章を読む。`ref` を持たない項目はheuristics.mdに対応する章が無い場合がある。そのときは `check`/`rule` 本文を根拠として扱い、原則名を捏造しない。

深刻度・確信度・出力仕様・運用ルールの定義は `uiux-checklist.yaml` を単一の正とする（本ファイルは実行に必要な範囲だけを再掲する）。

## 実行手順

1. **入力の種類を列挙する**。今回の入力が `code` / `screenshot` / `flow` / `runtime` のどれに当たるかを挙げる。複数該当しうる（コードとスクリーンショットが同時にあるのが最も多い）。
   - 入力が添付されていない場合は、ここで止まって入力を求める。一般論を語らない。
   - `runtime` を要求する項目があり、かつ起動可能なアプリが手元にある場合は、実際に操作して `runtime` を取得してから判定する（要確認に落とさない）。
   - ワイヤーフレームの場合は、視覚表現がまだ決まっていない項目（`A11Y-P-02` `A11Y-P-03` `GST-02` `TOKEN-01` `TOKEN-04`）を対象外にする。
2. **チェックリストを引く**。`uiux-checklist.yaml` の `items` を `category` 単位で走査する。`requires` は OR なので、**いずれか1つでも手元にあれば判定を試みる**。全部揃っている場合のみ確信度を「確定」にでき、一部しか無ければ「推定」以下に落とす。`requires` のいずれも無い項目だけを「要確認」として質問形式で出す。
   - 後半の `category`（`ethics` / `mobile` / `performance` / `ia` / `onboarding` / `i18n` / `design_system` / `privacy` / `consistency`）は見落としやすい。ここまで到達したことを必ず確認する。
   - `auto` フィールドは将来のlintスクリプト用のメタデータであり、確信度の根拠にしない。
3. **narrative項目を補う**。yaml に id が無い観点を `uiux-heuristics.md` から拾う。対象は3章（アフォーダンス／マッピング／制約／概念モデル、無効化ボタンに理由を併記）、4章（閉合・共通運命）、5章（フィッツの法則・系列位置効果・美的ユーザビリティ効果）、8章（エラーサマリ・パスワード表示切替）、9章（結果を予告する・主語をユーザーにする・謝罪より次の行動）、10章（強制的な継続）、11章（横持ち／折りたたみ・片手操作・低速回線）、13章（検索と閲覧の両方の経路）、14章（進捗の可視化が過度な圧力になっていないか）、15章（RTL・桁区切り）、17章（プラットフォームガイドライン全体）。
4. **良い点は指摘が3件以上あるときのみ1〜2件挙げる**。指摘だけに偏ると改善の方向を誤らせるため。無ければ省略してよく、無理に捻り出さない。
5. **件数より優先度**を意識する。低深刻度の指摘を大量に出すより、高深刻度を絞って出す方が価値がある（目安: 高3件、低は20件も出さない）。`note` に「片方のみ出す」とある重複ペアは、同じ事象から2件出さない。
6. **機械チェックを最後に走査する**。コードがある場合、以下は grep 相当で確実に判定できるうえ見落としやすい。出力を書き終える前に、この表を上から順に必ず確認する。

   | 見るもの | id |
   |---|---|
   | `<html>` に `lang` | `A11Y-U-01` |
   | `<img>` に `alt`（装飾は `alt=""`） | `A11Y-P-01` |
   | 入力欄に `label for` / `aria-label` | `A11Y-U-02` / `FORM-01` |
   | `outline: none` の置き去り | `A11Y-O-02` |
   | 正の `tabindex` | `A11Y-O-03` |
   | 動的更新領域に `aria-live` / `role="status"` / `role="alert"` | `A11Y-R-03` |
   | 繰り返しを飛ばす手段（スキップリンク / ランドマーク / 見出し） | `A11Y-O-10` |
   | `div`/`span` に `onclick` | `A11Y-R-02` |
   | viewport の `user-scalable=no` / `maximum-scale` | `MOB-06` |
   | 入力欄の `type` / `inputmode` / `autocomplete` | `FORM-02` / `FORM-03` |
   | チェックボックスの `checked` 初期値 | `DARK-01` |
   | `:hover` でしか出ない情報 | `MOB-05` |

   該当が無ければ「問題なし」と判断してよいが、**確認自体を飛ばさない**。

## 出力フォーマット

出力全体は次の順で構成する（`uiux-checklist.yaml` の `output_structure`）。

1. サマリ（3行以内。高が何件か、最優先の1件は何か）
2. 深刻度: 高 → 中 → 低 の順。`category` 順・id順にはしない
3. 要確認（別枠。質問形式）
4. 良い点（手順4の条件を満たすときのみ。深刻度・確信度は付けない）

指摘が0件の場合は「指摘なし」と明記し、代わりに要確認を厚く出す。

指摘は1件ずつ以下の形式で出す（`uiux-checklist.yaml` の `output_format`）。`id` はチェックリストにある項目ならそのid（例: `A11Y-P-01`）、チェックリストに無いnarrative項目は `[narrative: 原則名]` と書いてidと区別する。

```
[深刻度: 高/中/低] [確信度: 確定/推定/要確認] [id] 対象箇所
  問題: 何が起きているか
  根拠: どの入力から判断したか（該当コード行 / スクショの箇所 / 原則名）
  影響: ユーザーがどう困るか
  改善案: 具体的な変更内容
```

yaml の英語キーは出力時に日本語へ置き換える（`high`=高 / `medium`=中 / `low`=低、`confirmed`=確定 / `inferred`=推定 / `needs_check`=要確認）。深刻度・確信度の判定基準は `uiux-checklist.yaml` の `enums` を参照する。

推測を事実として断定しない。「〜のはずです」ではなく「〜か確認してください」と書く。コントラスト比を書くときは実際に計算し、採用した前景色・背景色・文字サイズを併記する。AAA の達成基準は、AA 適合を目標とする案件では「違反」と書かず推奨として出す。
