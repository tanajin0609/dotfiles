## 0. 入力の種類と判定できる範囲

**最初に必ず確認する。** 入力によって判定できる項目が変わり、これを無視すると「スクリーンショットしか無いのにキーボード操作性を断定する」ような誤指摘が出る。

| 入力 | 判定できる | 判定できない |
|---|---|---|
| **スクリーンショット1枚** | レイアウト、情報量、視覚的階層、コントラスト（概算）、文言 | キーボード操作、DOM構造、遷移、応答速度 |
| **HTML/CSS/コード** | セマンティクス、alt、label紐付け、コントラスト（厳密）、フォーカス、タップ領域 | 実際の見え方の印象、フロー全体 |
| **画面遷移図・フロー** | 完結感、エラー復帰導線、ステップ数、主導権 | 個々の画面の細部 |
| **実機・動作環境** | ほぼ全て | — |

判定に必要な入力が無い項目は、**指摘せずに「要確認」として別枠に出す**。断定しないこと。

## 1. ニールセン ユーザビリティ10原則

ヒューリスティック評価の標準。まずこれを土台にする。

### 1-1. システム状態の可視性

今何が起きているかを、適切な時間内にフィードバックする。

- **チェック**: 非同期処理にローディング表示があるか / 現在地がナビで分かるか / 保存が完了したと分かるか
- **NG**: 送信ボタンを押しても無反応。ユーザーが二重送信する
- **OK**: ボタンがスピナーに変わり、完了後にトースト表示

### 1-2. 現実世界とシステムの一致

ユーザーの言葉・概念で語る。システム内部の用語を漏らさない。

- **チェック**: エラーメッセージにコードや内部用語が出ていないか / アイコンの意味が一般的か
- **NG**: 「Transaction failed: 500」
- **OK**: 「お支払いを完了できませんでした。カード情報をご確認ください」

### 1-3. ユーザーの制御と自由

誤操作からの「非常口」を用意する。

- **チェック**: 取り消し・戻る手段があるか / モーダルを閉じられるか / 破壊的操作を取り消せるか
- **NG**: 削除したら即座に消えて復元不能
- **OK**: 削除後に「元に戻す」を数秒間表示（Gmailのアーカイブ取り消し）

### 1-4. 一貫性と標準

同じものは同じ見た目・同じ言葉・同じ位置に。

- **チェック**: 主要アクションの配置が画面間で揃っているか / 用語がぶれていないか（「登録」と「申込」の混在）
- **NG**: 画面Aは右下に「保存」、画面Bは左上に「確定」
- **OK**: 全画面で右下に「保存」

### 1-5. エラーの防止

そもそも間違えられない設計にする。

- **チェック**: 自由入力を選択式にできないか / 危険な操作に確認があるか / 入力形式を事前に示しているか
- **NG**: 日付をテキスト入力させて形式エラーを出す
- **OK**: カレンダーピッカーで選ばせる

### 1-6. 記憶より認識

覚えさせない。画面上に見せる。

- **チェック**: 前画面の情報を覚えている前提になっていないか / 入力候補やヒントを出しているか
- **NG**: 確認画面に金額しか出ず、選んだプラン名を思い出す必要がある
- **OK**: 確認画面に選択内容を全て再掲する

### 1-7. 柔軟性と効率性

初心者にも熟練者にも対応する。

- **チェック**: 頻繁な操作にショートカット・一括操作があるか / よく使う設定を保存できるか
- **例**: 一覧のチェックボックス一括削除、キーボードショートカット、直近の入力の再利用

### 1-8. 美的で最小限のデザイン

情報を盛らない。重要なものが埋もれない。

- **チェック**: 1画面の主目的が1つに絞れているか / CTAが複数競合していないか
- **NG**: 同じ強さのボタンが画面に5つ並ぶ
- **OK**: プライマリ1つ、他はセカンダリ／テキストリンク

### 1-9. エラーからの回復支援

原因と次の行動を平易な言葉で示す。

- **チェック**: 「何が」「なぜ」「どうすれば」の3点が揃っているか / エラー箇所が特定できるか
- **NG**: 「入力に誤りがあります」（どこか分からない）
- **OK**: 該当欄を赤枠にし「パスワードは8文字以上で入力してください」

### 1-10. ヘルプとドキュメント

理想は不要だが、必要なときにその場で参照できること。

- **チェック**: 迷いやすい入力欄に補足があるか / ヘルプが文脈内にあるか（別サイトへ飛ばさない）
- **例**: セキュリティコード欄の横にカード図解のツールチップ

## 2. シュナイダーマン 8つの黄金律

ニールセンと重複が多いが、**独自の観点**が2つある。

| # | 原則 | 備考 |
|---|---|---|
| 1 | 一貫性を保つ | ニールセン1-4と同義 |
| 2 | 普遍的な使いやすさ（初心者〜熟練者） | ニールセン1-7と同義 |
| 3 | 有益なフィードバックを返す | ニールセン1-1と同義 |
| 4 | 完結感のある対話をデザインする | **独自**：操作の始まり・中間・終わりを明示し、終了時に達成感を与える |
| 5 | エラーを防ぐ／簡単に回復させる | ニールセン1-5, 1-9 |
| 6 | 操作を簡単に取り消せる | ニールセン1-3 |
| 7 | 主導権はユーザーにある感覚を保つ | **独自**：システムに操られている感を与えない（予期せぬ自動遷移、勝手な設定変更） |
| 8 | 短期記憶の負荷を減らす | ニールセン1-6 |

- **7のNG例**: フォーム入力中に自動でページ遷移する／同意なくメルマガ登録がデフォルトON
- **4のOK例**: ステップ表示（1/3 → 2/3 → 3/3）と完了画面

## 3. ノーマンの設計原則

「見ただけで使い方が分かるか」を評価する軸。

| 概念 | 意味 | 例 |
|---|---|---|
| **アフォーダンス** | モノが提供する操作の可能性 | ボタンは押せる、スライダーは動かせる |
| **シグニファイア** | その可能性を伝える手がかり | 影、下線、ホバー時のカーソル変化 |
| **マッピング** | 操作と結果の対応関係 | コンロのつまみの配置＝五徳の配置 |
| **フィードバック** | 操作結果の即時提示 | タップ時のリップル、押下状態 |
| **制約** | できないことを物理的・論理的に封じる | 未入力時はボタンを無効化 |
| **概念モデル** | ユーザーが頭の中に作る動作イメージ | 「ゴミ箱に入れる＝あとで戻せる」 |

- **よくある指摘**: フラットデザインでシグニファイアが消え、押せる要素とただの文字の区別がつかない
- **補足（制約の使いすぎ）**: 無効化ボタンは「なぜ押せないか」が見えないと制約ではなく行き止まりになる。無効化するなら理由を併記するか、押させてエラーを返す方が親切な場合がある

## 4. ゲシュタルト原則（レイアウト）

見た目のまとまりを評価する。「余白でグルーピングできているか」が主眼。

| 原則 | 内容 | チェック観点 |
|---|---|---|
| **近接** | 近いものは同じグループに見える | ラベルが自分の入力欄より隣の欄に近くないか |
| **類同** | 似た形・色は同じ仲間に見える | 同じ役割のボタンが同じ見た目か |
| **閉合** | 欠けた形も補完して認識する | 罫線を減らしても表として読めるか |
| **連続** | 並びは線として追われる | 揃えるべき要素が揃っているか |
| **図と地** | 前景と背景の分離 | モーダルと背景のコントラストは十分か |
| **共通運命** | 同じ動きをするものは仲間 | アニメーションが意味の塊と一致しているか |

- **NG例**: 見出しと本文の間隔が、前のセクションとの間隔と同じ → どこで区切れるか分からない

## 5. Laws of UX（認知の法則）

数値目安が伴うため、レビュー時に具体的な指摘がしやすい。

| 法則 | 内容 | 目安・適用例 |
|---|---|---|
| **フィッツの法則** | ターゲットは大きく近いほど速く正確に押せる | 頻用ボタンは親指の届く下部に。※「44×44px」はAppleの指針であってフィッツの法則そのものではない |
| **ヒックの法則** | 選択肢が増えるほど決定に時間がかかる | メニューは階層化して1階層あたりを絞る。プランは3つ程度 |
| **ミラーの法則** | 短期記憶の限界 | 原典（Miller 1956）は7±2、近年の研究（Cowan）は4±1。**数値を断定せず「チャンク化する」という含意を使う**。電話番号をハイフンで区切る等 |
| **ヤコブの法則** | ユーザーは他サイトでの慣れを持ち込む | ロゴは左上でトップへ、カートは右上。独自すぎるUIは避ける |
| **ドハティのしきい値** | 応答が400ms以内だと作業に没入できる | 遅い処理はスケルトンや楽観的UIで体感を短縮 |
| **系列位置効果** | 最初と最後が記憶に残りやすい | 重要なナビ項目を両端に置く |
| **テスラーの法則** | 複雑さの総量は減らせない。誰が引き受けるか | 複雑さをシステム側に寄せる（住所の自動補完） |
| **ピークエンドの法則** | 体験はピークと終わりで評価される | 完了画面・エラー時の体験に注力する |
| **美的ユーザビリティ効果** | 見た目が良いと使いやすいと感じられる | ただし本質的な問題を隠すので過信しない |

## 6. WCAG 2.2 / POUR（アクセシビリティ）

機械的に判定しやすくスキル化と相性が良い。以下はWCAG 2.2 AA相当の代表項目。

> **2.1からの主な変更**: 達成基準が9つ追加（うちAA相当は 2.4.11 フォーカスの非隠蔽、2.5.7 ドラッグ動作、2.5.8 ターゲットのサイズ最小、3.3.8 アクセシブルな認証）。逆に 4.1.1（構文解析）は廃止された。

### P — 知覚可能（Perceivable）

- [ ] 画像に代替テキスト（装飾画像は `alt=""`）
- [ ] テキストのコントラスト比 4.5:1 以上（大きい文字は 3:1）
- [ ] UI部品・グラフの境界のコントラスト 3:1 以上（1.4.11）
- [ ] 色だけで情報を伝えていない（エラーを赤色のみで示さない）
- [ ] 動画に字幕
- [ ] 320px幅（400%ズーム相当）で横スクロールなく読める（1.4.10 リフロー）
- [ ] テキスト間隔を変更しても崩れない（1.4.12）

### O — 操作可能（Operable）

- [ ] キーボードのみで全機能を操作できる
- [ ] フォーカスリングが視認できる（`outline: none` の放置がないか）
- [ ] フォーカス順序が視覚順序と一致
- [ ] タブトラップがない（モーダル内は意図的なトラップが正解）
- [ ] 自動再生・自動スライドを停止できる
- [ ] タップ領域が十分な大きさ（**2.2で新設: 最小 24×24 CSS px**。Apple 44pt / Material 48dp はより厳しい推奨値）
- [ ] **フォーカス中の要素が固定ヘッダー等で隠れない（2.4.11 / 新設）**
- [ ] **ドラッグ操作に単一ポインタの代替がある（2.5.7 / 新設）** 例: 並べ替えD&Dに「上へ/下へ」ボタン
- [ ] `prefers-reduced-motion` を尊重している（2.3.3 関連）
- [ ] スキップリンクがある（2.4.1）

### U — 理解可能（Understandable）

- [ ] `<html lang="ja">` が指定されている
- [ ] フォームの `label` が入力欄と紐付いている（`for` / `id`）
- [ ] エラーが具体的で修正方法が分かる
- [ ] 予期せぬ文脈変化がない（選択しただけで送信されない）
- [ ] **同じ情報を再入力させない（3.3.7 / 新設）** 例: 配送先と請求先のコピー
- [ ] **認証で記憶・パズルを要求しない（3.3.8 / 新設）** 例: パスワードマネージャのペーストを禁止しない
- [ ] **ヘルプの導線が全画面で同じ位置にある（3.2.6 / 新設）**

### R — 堅牢（Robust）

- [ ] 見出しレベルが飛んでいない（h1 → h3 など）
- [ ] セマンティックなHTML（`div` にクリックイベントでなく `button`）
- [ ] 動的変更が支援技術に伝わる（`aria-live`）
- [ ] ステータスメッセージに `role="status"` 等（4.1.3）

## 7. UIの状態設計（6つの状態）

**新規追加。** 実装漏れが最も多い領域。デザインは「理想状態」だけ描かれがちで、残り5つが未定義のまま実装に渡る。

| 状態 | 内容 | チェック観点 |
|---|---|---|
| **空（Empty）** | データが0件 | 白紙でないか。次の行動（作成ボタン）を示せているか |
| **読込中（Loading）** | 取得待ち | スピナーよりスケルトン。400ms未満なら出さない方が良い場合も |
| **エラー（Error）** | 取得・送信失敗 | 再試行手段があるか。全画面エラーにせず部分で留められないか |
| **部分（Partial）** | 一部だけ取得できた | 取れた分を先に見せているか |
| **理想（Ideal）** | 通常表示 | — |
| **オフライン／権限なし** | 通信断・権限不足 | 操作の結果を失わないか |

- **NG**: 一覧が0件のとき、ヘッダーだけの真っ白な画面
- **OK**: 「まだ予約はありません」＋説明1行＋「予約を作成」ボタン

**空状態の3分類**（区別すると指摘が具体的になる）
1. **初回**（まだ何も作っていない）→ 使い方を教えるチャンス
2. **検索・絞り込みの結果0件** → 条件の解除手段を出す
3. **ユーザーが片付け終えた** → 労いを出してよい（受信箱ゼロ）

## 8. フォーム設計

**新規追加。** ニールセン1-5の下位に埋もれていた具体則を独立させる。

### 入力欄

- **チェック**: `label` を可視で置いているか（プレースホルダーをラベル代わりにしていないか）
- **NG**: プレースホルダーだけ。入力を始めた瞬間に何の欄か分からなくなる
- **OK**: ラベルは常時表示、プレースホルダーは書式例に使う

- モバイルで適切なキーボードが出るか（`inputmode="numeric"`、`type="email"`）
- `autocomplete` 属性でブラウザ補完が効くか（`autocomplete="postal-code"` 等）
- 入力欄の幅が想定文字数と対応しているか（郵便番号欄が氏名欄と同じ幅なのは誤り）
- 全角/半角、ハイフン有無を**システム側で吸収**しているか（テスラーの法則）

### バリデーション

- **タイミング**: 入力中(`onChange`)に赤字を出さない。フォーカスが外れた時(`onBlur`)、または送信時
- 一度エラーになった欄は、修正中にリアルタイムで解除してよい
- 送信時は最初のエラー欄へフォーカスを移す
- エラーサマリをフォーム冒頭に置く（項目数が多い場合）

### 必須・任意

- **チェック**: 必須が多数なら「任意」側に印を付ける
- `*` のみで示さず「必須」と文字で書く（色・記号依存の回避）

### その他

- 送信ボタンの二重押下を防いでいるか（`disabled` ＋ 状態表示）
- 送信失敗時に入力内容が保持されるか（**最頻出の重大バグ**）
- 長いフォームは自動保存または離脱警告があるか
- パスワード表示切替があるか

## 9. マイクロコピー

**新規追加。** コード変更が小さく効果が大きいため、指摘のコスパが高い。

| 観点 | NG | OK |
|---|---|---|
| **ボタンは動詞＋目的語** | 「送信」「OK」 | 「予約を確定する」 |
| **結果を予告する** | 「次へ」 | 「確認画面へ進む」（まだ確定しない安心感） |
| **二重否定を避ける** | 「通知を受け取らない ☐」 | 「通知を受け取る ☑」 |
| **ダイアログの選択肢を明示** | 「変更を破棄しますか？ [OK][キャンセル]」 | 「[破棄する][編集に戻る]」 |
| **主語をユーザーにする** | 「システムが処理を完了しました」 | 「保存しました」 |
| **謝罪より次の行動** | 「申し訳ございません。エラーが発生しました」 | 「読み込めませんでした。[再試行]」 |
| **数値・単位を具体的に** | 「しばらくお待ちください」 | 「1分ほどかかります」 |

## 10. ダークパターンと設計倫理

**新規追加。** シュナイダーマン第7律（主導権）の裏返し。近年は法規制（EU DSA、日本の特商法、景表法）にも関わるため、深刻度を高く扱う。

| パターン | 内容 | 指摘例 |
|---|---|---|
| **プリセレクション** | 同意・オプションがデフォルトON | メルマガ登録の初期チェック |
| **ローチモーテル** | 入るのは簡単、出るのが困難 | 登録はWeb1分、解約は電話のみ |
| **偽の緊急性・希少性** | 根拠のないカウントダウン、「残り1室」 | 実在しない在庫表示は景表法上のリスク |
| **コンファームシェイミング** | 断る選択肢を自虐的に書く | 「いいえ、損をしてもいい」 |
| **ミスディレクション** | 視覚的誘導で本来の選択肢を隠す | 「同意しない」だけ薄いグレーのテキスト |
| **隠れコスト** | 最終画面で費用が増える | 決済直前に手数料が出現 |
| **強制的な継続** | 無料期間終了時に無告知で課金 | 事前通知が無い |
| **ナグ（しつこい要求）** | 同じ依頼を繰り返す | 毎起動でアプリ評価を要求 |

- **判定の原則**: 「ユーザーの利益とビジネスの利益が対立する箇所で、UIがどちらに寄っているか」を見る
- **注意**: 意図の断定は避ける。「意図的に騙している」ではなく「この配置はダークパターンに該当しうる」と書く

---

## 11. モバイル固有

**新規追加。** フィッツの法則の実務版。

- **サムゾーン**: 画面下部1/3が最も押しやすい。破壊的操作を親指の自然な位置に置かない
- **ソフトキーボードで入力欄・送信ボタンが隠れないか**（iOSで頻発）
- **セーフエリア**: ノッチ、ホームインジケーター、Dynamic Island の回避
- **横持ち・折りたたみ端末での破綻**
- **スワイプの競合**: 横スワイプのカルーセルと、OSの「戻る」スワイプの衝突
- **プルトゥリフレッシュと縦スクロールの競合**
- **片手操作**: 上部のみに主要導線を置いていないか
- **通信断・低速回線での挙動**
- **タップ後のホバー残留**（モバイルには hover が無い前提で設計されているか）

## 12. 体感速度とパフォーマンス

**新規追加。** ドハティのしきい値に測定可能な裏付けを与える。Core Web Vitals の目安値：

| 指標 | 内容 | 良好の目安 | UXへの影響 |
|---|---|---|---|
| **LCP** | 主要コンテンツの表示完了 | 2.5秒以内 | 「まだ何も出ない」の体感 |
| **INP** | 操作への応答性（2024年にFIDを置換） | 200ms以内 | タップしても反応しない感覚 |
| **CLS** | レイアウトのずれ | 0.1未満 | **読み込み中にボタンがずれて誤タップ** |

- **CLSはUXの指摘として特に有効**: 画像やバナーに寸法指定が無いと、押そうとした瞬間に位置が動く
- **待たせ方の設計**: 1秒未満は何も出さない／1〜10秒はスケルトンや進捗／10秒超は完了予告と離脱可能に
- **楽観的UI**: 送信結果を待たず先に反映し、失敗時に戻す（SNSのいいね）。ただし失敗時の巻き戻しを必ず設計する

---

## 13. 情報アーキテクチャとナビゲーション

**新規追加。** 単一画面では見えない構造の問題。

- 階層が深すぎないか（目安：主要機能まで3タップ以内）
- 現在地が分かるか（パンくず、タブのアクティブ表示）
- ラベルがユーザーの語彙か（「ソリューション」より「料金」）
- 404・権限エラーから復帰する導線があるか
- 検索と閲覧の両方の経路があるか
- URLが状態を反映しているか（タブ切替・絞り込み条件を共有・ブックマークできるか）
- ブラウザバックで期待通りの状態に戻るか（モーダルを開いた状態で戻ると全画面離脱、は典型的なNG）

---

## 14. オンボーディングと権限要求

**新規追加。**

- **権限は理由を説明してから要求する**
  - NG: 起動直後にいきなりOSの位置情報ダイアログ
  - OK: 「近くの店舗を表示するために位置情報を使います」の画面を挟んでから要求
- 拒否された後の代替手段があるか（手入力で郵便番号）
- チュートリアルを強制的に全画面で流していないか（スキップ可能か）
- 初回は「空状態」を使って教える方が、ツアーより定着しやすい
- 登録を後回しにできるか（ゲスト利用）
- 進捗の可視化（プロフィール完成度など）が過度な圧力になっていないか

---

## 15. 多言語・可変長テキスト

**新規追加。**

- 日本語→英語・ドイツ語で文字数が **1.3〜2倍** に伸びる。ボタン内で折り返す・はみ出す前提でレイアウトしているか
- 固定高さのカードで、タイトルが2行になると崩れないか
- 日付・通貨・住所・氏名の順序をロケール依存で組んでいるか
- RTL（アラビア語等）対応の要否
- 数値の桁区切り、単位の位置
- 文字列を画像に焼き込んでいないか（翻訳不能・拡大で劣化）

---

## 16. デザイントークンの整合

**新規追加。** 自動判定と相性が良い（分類A）。

- 色がパレット外の値になっていないか（`#3B82F6` の隣に `#3C83F7` が混ざる）
- 余白が4pt/8ptスケール外になっていないか（`padding: 13px`）
- フォントサイズの種類が多すぎないか（目安：1画面で4〜5種類まで）
- 角丸・影の値が統一されているか
- 同じ意味の色が別の役割に使われていないか（成功と情報が同じ緑）

---

## 17. プラットフォームガイドライン

OS標準との一貫性チェック用。

### Apple HIG（iOS）

- タップ領域 44×44pt 以上
- 戻るは左上／スワイプバック
- Safe Area、ノッチ・ホームインジケーター回避
- 標準コンポーネントの意味を変えない

### Material Design 3（Android）

- タップ領域 48×48dp 以上
- システムの戻る操作に対応（ジェスチャーナビゲーション含む）
- FAB は画面の主要アクション1つに限定
- エレベーション（影）で階層を表現

### Web

- レスポンシブのブレークポイント
- ブラウザバックで期待通りの状態に戻る
- URLが状態を反映している（タブ切替・検索条件）
- 拡大縮小を禁止していない（`user-scalable=no` は不可）

## 18. スキル化のための分類と出力仕様

### A. 自動／機械的にチェックできる項目

コード・DOM・スタイルから判定可能。

- WCAG（コントラスト比、alt、label紐付け、見出し階層、セマンティクス）
- タップ領域サイズ、フォーカス可視性
- `autocomplete` / `inputmode` の有無
- 用語のゆれ（同義語の混在検出）
- ボタン階層の競合（プライマリの複数配置）
- デザイントークン逸脱（パレット外の色、スケール外の余白）
- 画像の寸法指定漏れ（CLS要因）

### B. 目視レビューで判定する項目

スクリーンショットや画面仕様から判断。

- ニールセン10原則
- ゲシュタルト原則（余白・グルーピング）
- 情報量の過多、一貫性
- マイクロコピー
- 視覚的階層

### C. フロー全体で判定する項目

単一画面では判定できない。

- ステップの完結感（シュナイダーマン4）
- エラーからの回復導線
- 主導権の感覚（シュナイダーマン7）
- ピークエンド（完了画面・失敗時の体験）
- ダークパターン（解約導線など、複数画面にまたがる）
- 情報アーキテクチャ

### 出力フォーマット

```
[深刻度: 高/中/低] [確信度: 確定/推定/要確認] [原則: N-x] 対象箇所
  問題: 何が起きているか
  根拠: どの入力から判断したか（該当コード行 / スクショの箇所 / 原則名）
  影響: ユーザーがどう困るか
  改善案: 具体的な変更内容
```

**確信度の基準**（誤指摘を防ぐために追加）

| 確信度 | 基準 |
|---|---|
| 確定 | 与えられた入力から直接判定できる（コード上に `alt` が無い） |
| 推定 | 一般的にそうだが、入力からは断定できない（スクショ上ボタンに見えるが実装は不明） |
| 要確認 | 判定に必要な入力が無い。指摘ではなく質問として出す |

**深刻度の基準**（ニールセンの4段階を簡略化）

| 深刻度 | 基準 |
|---|---|
| 高 | タスクを完了できない／データを失う／法令リスクがある |
| 中 | 完了できるが著しく手間・誤操作を誘発 |
| 低 | 完了に支障はないが体験を損なう |

### レビュー時の注意

- **件数より優先度**: 低の指摘を20件出すより、高を3件出す方が価値がある
- **良い点も1〜2件挙げる**: 改善の方向を誤らせないため
- **推測で断定しない**: 「〜のはずです」ではなく「〜か確認してください」
- **原則名を必ず添える**: 指摘が好みの問題でないことを示すため
