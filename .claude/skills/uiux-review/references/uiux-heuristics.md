## 0. 入力の種類と判定できる範囲

**最初に必ず確認する。** 入力によって判定できる項目が変わり、これを無視すると「スクリーンショットしか無いのにキーボード操作性を断定する」ような誤指摘が出る。

| 入力 | 判定できる | 判定できない |
|---|---|---|
| **スクリーンショット1枚** | レイアウト、情報量、視覚的階層、コントラスト（概算）、文言 | キーボード操作、DOM構造、遷移、応答速度 |
| **HTML/CSS/コード** | セマンティクス、alt、label紐付け、コントラスト（宣言値が静的に追える場合のみ）、フォーカス、タップ領域 | 実際の見え方の印象、フロー全体 |
| **画面遷移図・フロー** | 完結感、エラー復帰導線、ステップ数、主導権 | 個々の画面の細部 |
| **実機・動作環境** | ほぼ全て | — |

判定に必要な入力が無い項目は、**指摘せずに「要確認」として別枠に出す**。断定しないこと。

ただしこの表は「その入力だけで何が見えるか」の目安であり、判定の可否は `uiux-checklist.yaml` の `requires` が決める。`requires` は OR なので、列挙されたうちの1つでも手元にあれば判定を試み、全部揃っていない場合は確信度を「推定」以下に落とす。

コントラスト比は、CSS変数・継承・`opacity`・グラデーション・画像背景が絡むと宣言値から算出色が決まらない。コードがあれば厳密に出せるとは限らないので、その場合は「推定」にするかレンダリング結果を要求する。

## 1. ニールセン ユーザビリティ10原則

ヒューリスティック評価の標準。まずこれを土台にする。

### 1-1. システム状態の可視性

今何が起きているかを、適切な時間内にフィードバックする。

- **チェック**: 非同期処理にローディング表示があるか / 現在地がナビで分かるか / 保存が完了したと分かるか
- **NG**: 送信ボタンを押しても無反応。ユーザーが二重送信する
- **OK**: ボタンがスピナーに変わり、完了後にトースト表示

### 1-2. 現実世界とシステムの一致

ユーザーの言葉・概念で語る。システム内部の用語を漏らさない。

- **チェック**: エラーメッセージにコードや内部用語が出ていないか / アイコンの意味が一般的か
- **NG**: 「Transaction failed: 500」
- **OK**: 「お支払いを完了できませんでした。カード情報をご確認ください」

### 1-3. ユーザーの制御と自由

誤操作からの「非常口」を用意する。

- **チェック**: 取り消し・戻る手段があるか / モーダルを閉じられるか / 破壊的操作を取り消せるか
- **NG**: 削除したら即座に消えて復元不能
- **OK**: 削除後に「元に戻す」を数秒間表示（Gmailのアーカイブ取り消し）

### 1-4. 一貫性と標準

同じものは同じ見た目・同じ言葉・同じ位置に。

- **チェック**: 主要アクションの配置が画面間で揃っているか / 用語がぶれていないか（「登録」と「申込」の混在）
- **NG**: 画面Aは右下に「保存」、画面Bは左上に「確定」
- **OK**: 全画面で右下に「保存」

### 1-5. エラーの防止

そもそも間違えられない設計にする。

- **チェック**: 自由入力を選択式にできないか / 危険な操作に確認があるか / 入力形式を事前に示しているか
- **NG**: 日付をテキスト入力させて形式エラーを出す
- **OK**: カレンダーピッカーで選ばせる

### 1-6. 記憶より認識

覚えさせない。画面上に見せる。

- **チェック**: 前画面の情報を覚えている前提になっていないか / 入力候補やヒントを出しているか
- **NG**: 確認画面に金額しか出ず、選んだプラン名を思い出す必要がある
- **OK**: 確認画面に選択内容を全て再掲する

### 1-7. 柔軟性と効率性

初心者にも熟練者にも対応する。

- **チェック**: 頻繁な操作にショートカット・一括操作があるか / よく使う設定を保存できるか
- **例**: 一覧のチェックボックス一括削除、キーボードショートカット、直近の入力の再利用

### 1-8. 美的で最小限のデザイン

情報を盛らない。重要なものが埋もれない。

- **チェック**: 1画面の主目的が1つに絞れているか / CTAが複数競合していないか
- **NG**: 同じ強さのボタンが画面に5つ並ぶ
- **OK**: プライマリ1つ、他はセカンダリ／テキストリンク

### 1-9. エラーからの回復支援

原因と次の行動を平易な言葉で示す。

- **チェック**: 「何が」「なぜ」「どうすれば」の3点が揃っているか / エラー箇所が特定できるか
- **NG**: 「入力に誤りがあります」（どこか分からない）
- **OK**: 該当欄を赤枠にし「パスワードは8文字以上で入力してください」

### 1-10. ヘルプとドキュメント

理想は不要だが、必要なときにその場で参照できること。

- **チェック**: 迷いやすい入力欄に補足があるか / ヘルプが文脈内にあるか（別サイトへ飛ばさない）
- **例**: セキュリティコード欄の横にカード図解のツールチップ

## 2. シュナイダーマン 8つの黄金律

ニールセンと重複が多いが、**独自の観点**が2つある。

| # | 原則 | 備考 |
|---|---|---|
| 1 | 一貫性を保つ | ニールセン1-4と同義 |
| 2 | 普遍的な使いやすさ（初心者〜熟練者） | ニールセン1-7と同義 |
| 3 | 有益なフィードバックを返す | ニールセン1-1と同義 |
| 4 | 完結感のある対話をデザインする | **独自**：操作の始まり・中間・終わりを明示し、終了時に達成感を与える |
| 5 | エラーを防ぐ／簡単に回復させる | ニールセン1-5, 1-9 |
| 6 | 操作を簡単に取り消せる | ニールセン1-3 |
| 7 | 主導権はユーザーにある感覚を保つ | **独自**：システムに操られている感を与えない（予期せぬ自動遷移、勝手な設定変更） |
| 8 | 短期記憶の負荷を減らす | ニールセン1-6 |

- **7のNG例**: フォーム入力中に自動でページ遷移する／同意なくメルマガ登録がデフォルトON
- **4のOK例**: ステップ表示（1/3 → 2/3 → 3/3）と完了画面

## 3. ノーマンの設計原則

「見ただけで使い方が分かるか」を評価する軸。

| 概念 | 意味 | 例 |
|---|---|---|
| **アフォーダンス** | モノが提供する操作の可能性 | ボタンは押せる、スライダーは動かせる |
| **シグニファイア** | その可能性を伝える手がかり | 影、下線、ホバー時のカーソル変化 |
| **マッピング** | 操作と結果の対応関係 | コンロのつまみの配置＝五徳の配置 |
| **フィードバック** | 操作結果の即時提示 | タップ時のリップル、押下状態 |
| **制約** | できないことを物理的・論理的に封じる | 未入力時はボタンを無効化 |
| **概念モデル** | ユーザーが頭の中に作る動作イメージ | 「ゴミ箱に入れる＝あとで戻せる」 |

- **よくある指摘**: フラットデザインでシグニファイアが消え、押せる要素とただの文字の区別がつかない
- **補足（制約の使いすぎ）**: 無効化ボタンは「なぜ押せないか」が見えないと制約ではなく行き止まりになる。無効化するなら理由を併記するか、押させてエラーを返す方が親切な場合がある

## 4. ゲシュタルト原則（レイアウト）

見た目のまとまりを評価する。「余白でグルーピングできているか」が主眼。

| 原則 | 内容 | チェック観点 |
|---|---|---|
| **近接** | 近いものは同じグループに見える | ラベルが自分の入力欄より隣の欄に近くないか |
| **類同** | 似た形・色は同じ仲間に見える | 同じ役割のボタンが同じ見た目か |
| **閉合** | 欠けた形も補完して認識する | 罫線を減らしても表として読めるか |
| **連続** | 並びは線として追われる | 揃えるべき要素が揃っているか |
| **図と地** | 前景と背景の分離 | モーダルと背景のコントラストは十分か |
| **共通運命** | 同じ動きをするものは仲間 | アニメーションが意味の塊と一致しているか |

- **NG例**: 見出しと本文の間隔が、前のセクションとの間隔と同じ → どこで区切れるか分からない

## 5. Laws of UX（認知の法則）

数値目安が伴うため、レビュー時に具体的な指摘がしやすい。

| 法則 | 内容 | 目安・適用例 |
|---|---|---|
| **フィッツの法則** | ターゲットは大きく近いほど速く正確に押せる | 頻用ボタンは親指の届く下部に。※「44×44pt」はAppleの指針であってフィッツの法則そのものではない（法則 MT = a + b·log₂(2A/W) に絶対寸法は現れない） |
| **ヒックの法則** | 選択肢が増えるほど決定に時間がかかる | メニューは階層化して1階層あたりを絞る。プランは3つ程度 |
| **ミラーの法則** | 短期記憶の限界 | 原典（Miller 1956）は7±2、近年の研究（Cowan 2001）は「3〜5チャンク」。**数値を断定せず「チャンク化する」という含意を使う**。電話番号をハイフンで区切る等。※「±2」はMillerの論文タイトルにしか出てこず、本文で測ったのは絶対判断のスパン。Miller自身が記憶スパンとの一致を「偶然」と書いているので、「メニュー項目は7個まで」のような適用に原典の根拠は無い |
| **ヤコブの法則** | ユーザーは他サイトでの慣れを持ち込む | ロゴは左上でトップへ、カートは右上。独自すぎるUIは避ける |
| **ドハティのしきい値** | 応答時間の短縮が生産性を比例以上に改善する | 原典（Doherty & Thadani, IBM 1982）の閾値はサブセカンドで、実測点は0.3秒。**広く流布する「400ms」は原典に無い**。「没入・思考の連続性」を言うなら R.B. Miller (1968) の2秒／0.1秒。遅い処理はスケルトンや楽観的UIで体感を短縮 |
| **系列位置効果** | 最初と最後が記憶に残りやすい | 重要なナビ項目を両端に置く |
| **テスラーの法則** | 複雑さの総量は減らせない。誰が引き受けるか | 複雑さをシステム側に寄せる（住所の自動補完） |
| **ピークエンドの法則** | 体験はピークと終わりで評価される | 完了画面・エラー時の体験に注力する |
| **美的ユーザビリティ効果** | 見た目が良いと使いやすいと感じられる | ただし本質的な問題を隠すので過信しない |

## 6. WCAG 2.2 / POUR（アクセシビリティ）

機械的に判定しやすくスキル化と相性が良い。以下は代表項目で、各行の末尾に適合レベルを付ける。**AAA の項目は、AA 適合を目標とする案件では「違反」ではなく推奨として出す。**

> **2.1からの主な変更**: 達成基準が9つ追加された。
> - Level A: 3.2.6 一貫したヘルプ / 3.3.7 冗長な入力
> - Level AA: 2.4.11 フォーカスの非隠蔽（最低限） / 2.5.7 ドラッグ動作 / 2.5.8 ターゲットのサイズ（最小） / 3.3.8 アクセシブルな認証（最低限）
> - Level AAA: 2.4.12 フォーカスの非隠蔽（拡張） / 2.4.13 フォーカスの外観 / 3.3.9 アクセシブルな認証（拡張）
>
> AA適合はAを包含するので、**AAを目指す案件で新たに必須になるのは6つ**（Aの2つ＋AAの4つ）。
> 逆に 4.1.1（構文解析）は2.2で削除された（Obsolete and removed）。2.0/2.1でも、HTML/XMLを使う内容では常に満たすものとして扱う旨のerrataが出ている。

### P — 知覚可能（Perceivable）

- [ ] 画像に代替テキスト（装飾画像は `alt=""`）（1.1.1 / A）
- [ ] テキストのコントラスト比 4.5:1 以上、大きい文字（18pt または 14pt 太字以上）は 3:1 以上（1.4.3 / AA）
- [ ] UI部品・グラフの境界のコントラスト 3:1 以上（1.4.11 / AA）。テキストとは別に走査する
- [ ] 色だけで情報を伝えていない（エラーを赤色のみで示さない）（1.4.1 / A）
- [ ] 収録済み動画に字幕（1.2.2 / A）。ライブ配信は別基準（1.2.4 / AA）。音声の無い動画は字幕ではなく代替コンテンツ（1.2.1 / A）
- [ ] 320px幅（400%ズーム相当）で横スクロールなく読める（1.4.10 リフロー / AA）
- [ ] テキスト間隔を変更しても崩れない（1.4.12 / AA）

### O — 操作可能（Operable）

- [ ] キーボードのみで全機能を操作できる（2.1.1 / A）
- [ ] フォーカスリングが視認できる（`outline: none` の放置がないか）（2.4.7 / AA）。2.4.7 が問うのは「可視インジケータが存在するか」だけで、そのコントラストは 1.4.11（AA）、サイズ・形状は 2.4.13（AAA）が担当する
- [ ] フォーカス順序が視覚順序と一致（2.4.3 / A）。`tabindex="-1"` は正当なので指摘しない
- [ ] タブトラップがない（2.1.2 / A）。モーダル内は意図的なトラップが正解であり違反ではない
- [ ] 自動再生・自動スライドを停止できる（2.2.2 / A）
- [ ] タップ領域が十分な大きさ（**2.2で新設: 2.5.8 / AA、最小 24×24 CSS px**）。ただし例外があり、文中のリンク（Inline）と、間隔が確保されている場合（Spacing: 中心に直径24 CSS pxの円を置いて他と交差しない）は適合する。寸法基準は4系統が併存する — WCAG AA 24 CSS px / WCAG 2.5.5 AAA 44 CSS px / Apple 44pt / Material 3 48dp
- [ ] **フォーカス中の要素が固定ヘッダー等で完全には隠れない（2.4.11 / AA / 新設）** 部分的な重なりはAAでは許容。全く隠れないことを求めるのは 2.4.12（AAA）
- [ ] **ドラッグ操作に単一ポインタの代替がある（2.5.7 / AA / 新設）** 例: 並べ替えD&Dに「上へ/下へ」ボタン
- [ ] `prefers-reduced-motion` を尊重している（**2.3.3 / AAA**。SC本文は「操作で起動するモーションを無効化できる」で、`prefers-reduced-motion` は達成方法。自動開始するモーションは 2.2.2 / A が担当）
- [ ] 繰り返しコンテンツを飛ばす手段がある（2.4.1 / A）。スキップリンクは達成方法の一つで、ARIAランドマーク・見出し構造でも適合する

### U — 理解可能（Understandable）

- [ ] `<html lang="ja">` が指定されている（3.1.1 / A）
- [ ] フォームの `label` が入力欄と紐付いている（`for` / `id`）（**1.3.1 / A**）。`aria-label` 等による代替名は 4.1.2（A）
- [ ] 入力欄に**可視の**ラベルまたは説明が提供されている（**3.3.2 / A**）。3.3.2 はマークアップの正しさも代替名の有無も問わない別基準なので、`aria-label` だけの実装は 4.1.2 を満たしても 3.3.2 は満たさない
- [ ] エラーが具体的で修正方法が分かる（3.3.1 / A でエラー箇所を示し、3.3.3 / AA で修正を示唆）
- [ ] 予期せぬ文脈変化がない（選択しただけで送信されない）（3.2.2 / A）
- [ ] **同じ情報を再入力させない（3.3.7 / A / 新設）** 例: 配送先と請求先のコピー
- [ ] **認証で記憶・パズルを要求しない（3.3.8 / AA / 新設）** 例: パスワードマネージャのペーストを禁止しない
- [ ] **ヘルプの導線が、他のコンテンツに対して常に同じ相対順序で現れる（3.2.6 / A / 新設）** 「同じ位置」ではないので、レスポンシブで表示位置が変わっても順序が保たれていれば適合する

### R — 堅牢（Robust）

- [ ] セマンティックなHTML（`div` にクリックイベントでなく `button`）（4.1.2 / A）
- [ ] 動的変更が支援技術に伝わる（`aria-live`）（4.1.3 / AA）
- [ ] ステータスメッセージに `role="status"` 等（4.1.3 / AA）
- [ ] 見出しレベルが飛んでいない（h1 → h3 など）― **これはWCAG適合基準ではない**。1.3.1 は情報と関係性がプログラム的に判別可能かのみを問い、見出しレベルのスキップも「h1は1つだけ」も要求していない。支援技術の見出しジャンプを損なうベストプラクティスとして扱い、WCAG違反とは書かない。見出しが内容を説明しているかを問うなら 2.4.6（AA）

## 7. UIの状態設計（6つの状態）

**新規追加。** 実装漏れが最も多い領域。デザインは「理想状態」だけ描かれがちで、残り5つが未定義のまま実装に渡る。

| 状態 | 内容 | チェック観点 |
|---|---|---|
| **空（Empty）** | データが0件 | 白紙でないか。次の行動（作成ボタン）を示せているか |
| **読込中（Loading）** | 取得待ち | スピナーよりスケルトン。1秒未満なら出さない方が良い場合も（12章の待たせ方の設計と同じ基準） |
| **エラー（Error）** | 取得・送信失敗 | 再試行手段があるか。全画面エラーにせず部分で留められないか |
| **部分（Partial）** | 一部だけ取得できた | 取れた分を先に見せているか |
| **理想（Ideal）** | 通常表示 | — |
| **オフライン／権限なし** | 通信断・権限不足 | 操作の結果を失わないか |

- **NG**: 一覧が0件のとき、ヘッダーだけの真っ白な画面
- **OK**: 「まだ予約はありません」＋説明1行＋「予約を作成」ボタン

**空状態の3分類**（区別すると指摘が具体的になる）
1. **初回**（まだ何も作っていない）→ 使い方を教えるチャンス
2. **検索・絞り込みの結果0件** → 条件の解除手段を出す
3. **ユーザーが片付け終えた** → 労いを出してよい（受信箱ゼロ）

## 8. フォーム設計

**新規追加。** ニールセン1-5の下位に埋もれていた具体則を独立させる。

### 入力欄

- **チェック**: `label` を可視で置いているか（プレースホルダーをラベル代わりにしていないか）
- **NG**: プレースホルダーだけ。入力を始めた瞬間に何の欄か分からなくなる
- **OK**: ラベルは常時表示、プレースホルダーは書式例に使う

- モバイルで適切なキーボードが出るか（`inputmode="numeric"`、`type="email"`）
- `autocomplete` 属性でブラウザ補完が効くか（`autocomplete="postal-code"` 等）
- 入力欄の幅が想定文字数と対応しているか（郵便番号欄が氏名欄と同じ幅なのは誤り）
- 全角/半角、ハイフン有無を**システム側で吸収**しているか（テスラーの法則）

### バリデーション

- **タイミング**: 入力中(`onChange`)に赤字を出さない。フォーカスが外れた時(`onBlur`)、または送信時
- 一度エラーになった欄は、修正中にリアルタイムで解除してよい
- 送信時は最初のエラー欄へフォーカスを移す
- エラーサマリをフォーム冒頭に置く（項目数が多い場合）

### 必須・任意

- **チェック**: 必須が多数なら「任意」側に印を付ける
- `*` のみで示さず「必須」と文字で書く（色・記号依存の回避）

### その他

- 送信ボタンの二重押下を防いでいるか（`disabled` ＋ 状態表示）
- 送信失敗時に入力内容が保持されるか（**最頻出の重大バグ**）
- 長いフォームは自動保存または離脱警告があるか
- パスワード表示切替があるか

## 9. マイクロコピー

**新規追加。** コード変更が小さく効果が大きいため、指摘のコスパが高い。

| 観点 | NG | OK |
|---|---|---|
| **ボタンは動詞＋目的語** | 「送信」「OK」 | 「予約を確定する」 |
| **結果を予告する** | 「次へ」 | 「確認画面へ進む」（まだ確定しない安心感） |
| **二重否定を避ける** | 「通知を受け取らない ☐」 | 「通知を受け取る ☑」 |
| **ダイアログの選択肢を明示** | 「変更を破棄しますか？ [OK][キャンセル]」 | 「[破棄する][編集に戻る]」 |
| **主語をユーザーにする** | 「システムが処理を完了しました」 | 「保存しました」 |
| **謝罪より次の行動** | 「申し訳ございません。エラーが発生しました」 | 「読み込めませんでした。[再試行]」 |
| **数値・単位を具体的に** | 「しばらくお待ちください」 | 「1分ほどかかります」 |

## 10. ダークパターンと設計倫理

**新規追加。** シュナイダーマン第7律（主導権）の裏返し。法規制に関わるため深刻度を高く扱うが、**どの法令が効くかはパターンごとに違う**。「特商法と景表法がダークパターン一般を覆う」わけではない。

- **EU**: 本命は **UCPD（不公正商慣行指令 2005/29/EC）**。全事業者に水平適用され、欧州委員会の公式ガイダンスにダークパターン専用節がある。偽の緊急性・希少性は Annex I No.7（それ自体で禁止）、ナグは Annex I No.26、コンファームシェイミングは第8条、解約導線は第7条／第9条(d)。
  DSA 第25条は**残余的な規定**で、①「オンラインプラットフォーム」提供者に限られ（UGCを公衆配信しない通常のEC・SaaS・企業サイトは射程外）、②零細・小企業は適用除外、③UCPD や GDPR が捕捉するものは対象外と明記されている。
  同意画面は GDPR 第4条(11)・第7条(3)（「同意の撤回は付与と同じくらい容易でなければならない」）。
- **日本**: 解約妨害は特商法**第13条の2**（不実の告知の禁止）。無告知の自動課金には**消費者契約法第10条**（消費者の不作為を承諾とみなす条項は無効）が直接効く。景表法は表示の優良誤認・有利誤認が対象。
  ただし消費者庁自身が、現行の景表法では規制が及ばない領域があると報告書に記録している。**ローチモーテル・コンファームシェイミング・ナグは現行法の穴**にあたるため、「違法」と断定せず設計上の問題として指摘する。

| パターン | 内容 | 指摘例 |
|---|---|---|
| **プリセレクション** | 同意・オプションがデフォルトON | メルマガ登録の初期チェック |
| **ローチモーテル** | 入るのは簡単、出るのが困難 | 登録はWeb1分、解約は電話のみ |
| **偽の緊急性・希少性** | 根拠のないカウントダウン、「残り1室」 | 実在しない在庫表示は景表法上のリスク |
| **コンファームシェイミング** | 断る選択肢を自虐的に書く | 「いいえ、損をしてもいい」 |
| **ミスディレクション** | 視覚的誘導で本来の選択肢を隠す | 「同意しない」だけ薄いグレーのテキスト |
| **隠れコスト** | 最終画面で費用が増える | 決済直前に手数料が出現 |
| **強制的な継続** | 無料期間終了時に無告知で課金 | 事前通知が無い |
| **ナグ（しつこい要求）** | 同じ依頼を繰り返す | 毎起動でアプリ評価を要求 |

- **判定の原則**: 「ユーザーの利益とビジネスの利益が対立する箇所で、UIがどちらに寄っているか」を見る
- **注意**: 意図の断定は避ける。「意図的に騙している」ではなく「この配置はダークパターンに該当しうる」と書く

## 11. モバイル固有

**新規追加。** フィッツの法則の実務版。

- **サムゾーン**: 画面下部1/3が最も押しやすい。破壊的操作を親指の自然な位置に置かない
- **ソフトキーボードで入力欄・送信ボタンが隠れないか**（iOSで頻発）
- **セーフエリア**: ノッチ、ホームインジケーター、Dynamic Island の回避
- **横持ち・折りたたみ端末での破綻**
- **スワイプの競合**: 横スワイプのカルーセルと、OSの「戻る」スワイプの衝突
- **プルトゥリフレッシュと縦スクロールの競合**
- **片手操作**: 上部のみに主要導線を置いていないか
- **通信断・低速回線での挙動**
- **タップ後のホバー残留**（モバイルには hover が無い前提で設計されているか）

## 12. 体感速度とパフォーマンス

**新規追加。** ドハティのしきい値に測定可能な裏付けを与える。Core Web Vitals の目安値：

| 指標 | 内容 | 良好の目安 | UXへの影響 |
|---|---|---|---|
| **LCP** | 主要コンテンツの表示完了 | 2.5秒以下 | 「まだ何も出ない」の体感 |
| **INP** | 操作への応答性（2024-03-12にFIDを置換） | 200ms以下 | タップしても反応しない感覚 |
| **CLS** | レイアウトのずれ | 0.1以下 | **読み込み中にボタンがずれて誤タップ** |

- **CLSはUXの指摘として特に有効**: 画像やバナーに寸法指定が無いと、押そうとした瞬間に位置が動く
- **待たせ方の設計**: 1秒未満は何も出さない／1〜10秒はスケルトンや進捗／10秒超は完了予告と離脱可能に
- **楽観的UI**: 送信結果を待たず先に反映し、失敗時に戻す（SNSのいいね）。ただし失敗時の巻き戻しを必ず設計する

## 13. 情報アーキテクチャとナビゲーション

**新規追加。** 単一画面では見えない構造の問題。

- 階層が深すぎないか（目安：主要機能まで3タップ以内）
- 現在地が分かるか（パンくず、タブのアクティブ表示）
- ラベルがユーザーの語彙か（「ソリューション」より「料金」）
- 404・権限エラーから復帰する導線があるか
- 検索と閲覧の両方の経路があるか
- URLが状態を反映しているか（タブ切替・絞り込み条件を共有・ブックマークできるか）
- ブラウザバックで期待通りの状態に戻るか（モーダルを開いた状態で戻ると全画面離脱、は典型的なNG）

---

## 14. オンボーディングと権限要求

**新規追加。**

- **権限は理由を説明してから要求する**
  - NG: 起動直後にいきなりOSの位置情報ダイアログ
  - OK: 「近くの店舗を表示するために位置情報を使います」の画面を挟んでから要求
- 拒否された後の代替手段があるか（手入力で郵便番号）
- チュートリアルを強制的に全画面で流していないか（スキップ可能か）
- 初回は「空状態」を使って教える方が、ツアーより定着しやすい
- 登録を後回しにできるか（ゲスト利用）
- 進捗の可視化（プロフィール完成度など）が過度な圧力になっていないか

---

## 15. 多言語・可変長テキスト

**新規追加。**

- 日本語→英語・ドイツ語で文字数が **1.3〜2倍** に伸びる。ボタン内で折り返す・はみ出す前提でレイアウトしているか
- 固定高さのカードで、タイトルが2行になると崩れないか
- 日付・通貨・住所・氏名の順序をロケール依存で組んでいるか
- RTL（アラビア語等）対応の要否
- 数値の桁区切り、単位の位置
- 文字列を画像に焼き込んでいないか（翻訳不能・拡大で劣化）

---

## 16. デザイントークンの整合

**新規追加。** 自動判定と相性が良い（分類A）。

- 色がパレット外の値になっていないか（`#3B82F6` の隣に `#3C83F7` が混ざる）
- 余白が4pt/8ptスケール外になっていないか（`padding: 13px`）
- フォントサイズの種類が多すぎないか（目安：1画面で4〜5種類まで）
- 角丸・影の値が統一されているか
- 同じ意味の色が別の役割に使われていないか（成功と情報が同じ緑）

## 17. プラットフォームガイドライン

OS標準との一貫性チェック用。

### Apple HIG（iOS）

- ボタンのヒット領域は一般則として 44×44pt 以上（visionOS は 60×60pt）。ただしHIGのアクセシビリティ表では 44×44pt は iOS/iPadOS の *default* control size で、*minimum* は 28×28pt
- 戻るは左上／スワイプバック
- Safe Area、ノッチ・ホームインジケーター回避
- 標準コンポーネントの意味を変えない

### Material Design 3（Android）

- タップ領域は「多くのプラットフォームで 48×48dp 以上を検討する」（M3の表現は推奨であって最小規定ではない）。ターゲット間隔は 8dp。M3 の 24dp は**アイコンの見た目のサイズ**であって緩和規定ではない
- システムの戻る操作に対応（ジェスチャーナビゲーション含む）
- FAB は画面の主要アクション1つに限定
- エレベーション（影）で階層を表現

### Web

- レスポンシブのブレークポイント
- ブラウザバックで期待通りの状態に戻る
- URLが状態を反映している（タブ切替・検索条件）
- 拡大縮小を禁止していない（`user-scalable=no` は不可）

## 18. スキル化のための分類と出力仕様

### A. 自動／機械的にチェックできる項目

コード・DOM・スタイルから判定可能。

- WCAG（コントラスト比、alt、label紐付け、見出し階層、セマンティクス）
- タップ領域サイズ、フォーカス可視性
- `autocomplete` / `inputmode` の有無
- 用語のゆれ（同義語の混在検出）
- ボタン階層の競合（プライマリの複数配置）
- デザイントークン逸脱（パレット外の色、スケール外の余白）
- 画像の寸法指定漏れ（CLS要因）

### B. 目視レビューで判定する項目

スクリーンショットや画面仕様から判断。

- ニールセン10原則
- ゲシュタルト原則（余白・グルーピング）
- 情報量の過多、一貫性
- マイクロコピー
- 視覚的階層

### C. フロー全体で判定する項目

単一画面では判定できない。

- ステップの完結感（シュナイダーマン4）
- エラーからの回復導線
- 主導権の感覚（シュナイダーマン7）
- ピークエンド（完了画面・失敗時の体験）
- ダークパターン（解約導線など、複数画面にまたがる）
- 情報アーキテクチャ

### 出力仕様・確信度・深刻度・運用ルール

`uiux-checklist.yaml` を単一の正とする（`output_format` / `output_structure` / `enums` / `review_rules`）。ここには重複して置かない。

深刻度の3段階は、ニールセンの5段階（0〜4）を簡略化したもの。
