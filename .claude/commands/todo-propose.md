# /todo-propose — 提案書・作業計画書の作成（実装はしない）

対象サブプロジェクトの性質（dev系 / ops系）を自動判定し、既存資材を調査したうえで
提案書（dev系: `proposal.md`・`design.md`・`tasks.md`）または作業計画書（ops系: `plan.md`）を
埋める。**ここで必ず停止する。承認は人間が行い、実装はそのあとの別のやり取りで進める
（本コマンドは実装フェーズを持たない）。**

ディレクトリの雛形作成そのものは `/init-change`・`/init-ops-work` の責務であり、本コマンドは
重複させずそれらに委譲する（責務分割）。

## 引数

`$ARGUMENTS` の1トークン目に対象サブプロジェクト（`projects/` からの相対パス、例: `json-gui-editor`、
`ops-work/fix-points/<tenant>`）、残りに依頼内容・変更内容の説明を渡す。
例: `/todo-propose json-gui-editor feat-tree-dnd-reparent ツリーペインのD&Dによる親付け替え`

## ワークフロー

### 1. 対象タイプの判定

`<対象>/docs/specs/` の有無で判定する。

- **あり** → dev系。「A. dev系の場合」に進む。
- **なし** → ops系。「B. ops系の場合」に進む。
- **どちらとも言えない**（新規サブプロジェクトで未初期化）場合は判定を打ち切り、
  `/init-spec` または `/init-ops-work` の実行を提案する（提案のみ、勝手に実行しない）。

### 2. 既存資材の調査（省略禁止）

提案書・作業計画書を書く前に、以下を必ず確認する。

- 対象リポジトリ内に同種の処理を行う既存コード・ドキュメント・仕様がないか
- `git branch -a` で作業ブランチにしか無い資材がないか
- dev系の場合は関連する既存の `docs/changes/` エントリ、`docs/specs/` の該当節
- ops系の場合は既存の汎用バッチ・スクリプト（`self-work/directry-rules/directry-rules.md` 5章参照）

見つかった場合はそれを対応方針のベースにする。見つからなかった場合も
「調査した上で該当なし」と明記する。**この節を空のまま次に進まない**
（過去に既存の仕組みを知らず独自実装を一から書いてしまった経緯があるため。同5章参照）。

### A. dev系の場合

**A-1.** `docs/changes/` 配下に対応する変更ディレクトリが無ければ、
`/home/igpf-2500009/.claude/commands/init-change.md` のワークフロー（change-name確認・重複チェック・
バージョン算出・テンプレートコピー）に従って作成する。既にあれば流用する。

**A-2.** 手順2の調査結果と依頼内容をもとに、以下を埋める。**見出しは変更しない。**

| ファイル | 見出し | 書く内容 |
|---|---|---|
| `proposal.md` | 背景 | なぜこの変更が必要か。手順2の調査結果の要点を含める |
| `proposal.md` | 提案内容 | 何を・どの範囲で対応するか |
| `proposal.md` | 影響範囲 | 影響するファイル・機能・他サブプロジェクトとの依存 |
| `design.md` | アーキテクチャ | 既存構造のどこに手を入れるか |
| `design.md` | 実装方針 | 具体的な実装方針。既存資材があればそれをベースにする |
| `tasks.md` | 先頭のチェックリスト | 実装タスクの分解（delta specのチェック項目はテンプレートのまま残す） |

情報が不足している箇所は推測で埋めず、`proposal.md`の「影響範囲」または `design.md` に
質問として明記する（承認時のレビュー観点になる）。

**A-3.** `docs/tasks/todo.md` に以下の形式で1行追記する（未着手・承認待ちの残タスクとして
反映するため。既存の運用メモの区分に合わせる場所が無ければ新設してよい）。

```
- [ ] <change-name> — 提案中・承認待ち → docs/changes/<version>-<change-name>-<日付>/proposal.md
```

過去に提案が `todo.md` に一度も反映されず日次棚卸しから漏れた事例があるため
（`directry-rules.md` 4.3）、この追記は省略しない。

**A-4.** `docs/specs/`（大本spec）はこの時点では変更しない（Spec-First: 実装フェーズで直接更新し、
差分は `specs/` にunified diffで残す。`directry-rules.md` 4.2）。

### B. ops系の場合

**B-1.** 依頼に対応する `order-yyyymmdd/` が無ければ、
`/home/igpf-2500009/.claude/commands/init-ops-work.md` のワークフロー（対象ディレクトリ決定・
依頼ディレクトリ決定・重複チェック・テンプレートコピー・todo.md追記）に従って作成する。
既にあれば流用する。

**B-2.** `order.md` に依頼内容（何を・いつまでに・誰から）を書く（Notion等の外部ソースが無い、
その場で受けた依頼として書き起こす）。

**B-3.** 手順2の調査結果と依頼内容をもとに `plan.md` の以下の見出しを埋める。**見出しは変更しない。**

| 見出し | 書く内容 |
|---|---|
| 依頼概要 | order.mdの要約。何を・どの範囲で・なぜ |
| 調査結果 | 手順2の結果。参照したファイルパスを明記する |
| 対応方針 | 実装方針。既存資材があればそれをベースにする |
| 対象データ | 対象件数・データソース・整合性の確認結果 |
| リスク・確認事項 | 不可逆操作の有無、情報が不足している点を質問として残す |
| 承認状況 | テンプレートのチェックボックスをそのまま残す |

情報が足りない箇所は推測で埋めない。「リスク・確認事項」に質問として書き出す。

業務ルール（履歴レコードの備考欄への記録方式など）が
`/home/igpf-2500009/.claude/local/ops-work/RULES.md` にあれば読んで従う。無ければ黙って続行する。

**B-4.** `todo.md`（サブプロジェクト直下）への追記は `/init-ops-work` の手順内で行われる前提。
未追記なら本手順で追記する。

## 3. 完了報告と停止

以下を報告し、**ここで停止する。承認前提で `src/`・実装コードには着手しない。**

- 作成・更新したファイルのパス（`proposal.md`/`design.md`/`tasks.md` または `order.md`/`plan.md`、
  `todo.md` への追記）
- 手順2の調査結果の要点
- 「リスク・確認事項」または質問として残した項目（あれば箇条書きで再掲）
- 承認後は改めて実装を依頼してもらう旨（本コマンドは実装フェーズを持たない）

## 注意事項

- 本コマンドはディレクトリの雛形作成を行わない（`/init-change`・`/init-ops-work` の責務）。
  雛形が無ければそれらのワークフローに従って先に作成する（手順A-1/B-1）。
- 承認は人間が行う。AIが自己判定して次工程（実装）に進まない。
- dev系・ops系いずれも、既存資材の調査（手順2）を省略しない。
- 案件固有の業務ルールは本コマンドに書かない。ops系の業務ルール参照先は
  `/home/igpf-2500009/.claude/local/ops-work/RULES.md`（無ければ黙って続行）。
