# /todo-propose — 提案書・作業計画書の作成（実装はしない）

対象サブプロジェクトの性質（dev系 / ops系）を自動判定し、既存資材を調査したうえで
提案書（dev系: `proposal.md`・`design.md`・`tasks.md`）または作業計画書（ops系: `plan.md`）を
埋める。**ここで必ず停止する。承認は人間が行い、実装はそのあとの別のやり取りで進める
（本コマンドは実装フェーズを持たない）。**

ディレクトリの雛形作成そのものは `/init-change`・`/init-ops-work` の責務であり、本コマンドは
重複させずそれらに委譲する（責務分割）。

## 引数

`$ARGUMENTS` の1トークン目に対象サブプロジェクト（`projects/` からの相対パス、例: `json-gui-editor`、
`ops-work/fix-points/<tenant>`）、残りに依頼内容・変更内容の説明を渡す（単一対象モード）。
例: `/todo-propose json-gui-editor feat-tree-dnd-reparent ツリーペインのD&Dによる親付け替え`

`$ARGUMENTS` が空の場合は下記の「today-todoバッチモード」で動作する。

## today-todoバッチモード（引数なし）

`~/projects/today-todo/todo-YYYY-MM-DD.md`（実行時のシステム日付）を入力に、
複数サブプロジェクトの未完了項目をまとめて処理する。`/todo-import` が生成する前提のファイル。

ファイルが存在しなければ `/todo-import` の実行を提案して停止する（勝手に生成しない）。

### 0-1. サブプロジェクト単位でグルーピング

ファイル内の `##` 見出し（サブプロジェクト名）ごとに未完了項目（`- [ ]`）を集める。ネストした
子チェックボックスは親項目の一部として扱う。

### 0-2. サブプロジェクトごとにサブエージェントを並列起動

サブプロジェクト数ぶんの Agent を**単一メッセージで並列**起動する。1サブエージェント＝
1サブプロジェクト＝そのサブプロジェクトの担当項目全部（同一サブプロジェクト内での調査重複や
同一 change/order ディレクトリの競合を避けるため、項目単位には分割しない）。

各サブエージェントへの指示に含めるもの:

- 対象サブプロジェクトのパスと、担当する未完了項目一覧（todo-YYYY-MM-DD.md の記述をそのまま渡す。
  要約・間引きをしない）
- 下記「0-3. 項目ごとの一次判定」の基準
- 「新規提案が必要」と判定した項目には下記「## ワークフロー」（手順1・2、A/B）をそのまま実行させる
- 完了後は「0-4. 報告フォーマット」で報告させる

サブエージェントの model は model-routing skill の基準に従う。本タスクは調査結果の解釈と
提案文の起案という「判断・統合」に当たり、誤判定がそのまま資産（見落とし・的外れな提案書）に
なるため、既定モデル（ダウングレードしない）を用いる。

### 0-3. 項目ごとの一次判定（サブエージェントが実施）

各項目について、提案書/作業計画書の起票が必要かを判定する。

| 分類 | 判定基準 | 扱い |
|---|---|---|
| 新規提案が必要 | 対応方針が未確定で、コード変更・作業計画の起票余地がある | 「## ワークフロー」を実行 |
| 既に提案済み・進行中 | 対応する `docs/changes/`・`order-*/` が既にあり内容も埋まっている | 起票せずスキップ（既存パスを報告） |
| 人間の決定待ちで対象外 | 外部承認・外部ブロッカーなど、AIの提案書化では前に進まない事項 | スキップ（理由を報告） |
| 物理作業などで対象外 | 現地検証・現地設定確認など、提案書という成果物になじまない作業 | スキップ（理由を報告） |

判定に迷う場合は「新規提案が必要」に倒さず、根拠とともに対象外寄りに分類して理由を明記する
（過剰生成よりも判断を保留してユーザーに戻す方を優先する）。

### 0-4. サブエージェントの報告フォーマット

担当項目ごとに以下を報告させる。

- 項目内容（todo-YYYY-MM-DD.md の記述そのまま）
- 分類（0-3の4区分のいずれか）
- 「新規提案が必要」の場合: 作成・更新したファイルパス、手順2の調査結果の要点、
  リスク・確認事項/質問
- スキップの場合: 理由

todo-YYYY-MM-DD.md 自体への書き込み（チェック付け等）は行わない。進捗の一次情報は各サブプロジェクトの
`todo.md`・変更ディレクトリ側に持たせる（`/todo-import` が次回実行時に反映する）。

## ワークフロー

### 1. 対象タイプの判定

`<対象>/docs/specs/` の有無で判定する。

- **あり** → dev系。「A. dev系の場合」に進む。
- **なし** → ops系。「B. ops系の場合」に進む。
- **どちらとも言えない**（新規サブプロジェクトで未初期化）場合は判定を打ち切り、
  `/init-spec` または `/init-ops-work` の実行を提案する（提案のみ、勝手に実行しない）。

### 2. 既存資材の調査（省略禁止）

提案書・作業計画書を書く前に、以下を必ず確認する。

- 対象リポジトリ内に同種の処理を行う既存コード・ドキュメント・仕様がないか
- `git branch -a` で作業ブランチにしか無い資材がないか
- dev系の場合は関連する既存の `docs/changes/` エントリ、`docs/specs/` の該当節
- ops系の場合は既存の汎用バッチ・スクリプト（`self-work/directry-rules/directry-rules.md` 5章参照）

見つかった場合はそれを対応方針のベースにする。見つからなかった場合も
「調査した上で該当なし」と明記する。**この節を空のまま次に進まない**
（過去に既存の仕組みを知らず独自実装を一から書いてしまった経緯があるため。同5章参照）。

### A. dev系の場合

**A-1.** `docs/changes/` 配下に対応する変更ディレクトリが無ければ、
`~/.claude/commands/init-change.md` のワークフロー（change-name確認・重複チェック・
バージョン算出・テンプレートコピー）に従って作成する。既にあれば流用する。

**A-2.** 手順2の調査結果と依頼内容をもとに、以下を埋める。**見出しは変更しない。**

| ファイル | 見出し | 書く内容 |
|---|---|---|
| `proposal.md` | 背景 | なぜこの変更が必要か。手順2の調査結果の要点を含める |
| `proposal.md` | 提案内容 | 何を・どの範囲で対応するか |
| `proposal.md` | 影響範囲 | 影響するファイル・機能・他サブプロジェクトとの依存 |
| `design.md` | アーキテクチャ | 既存構造のどこに手を入れるか |
| `design.md` | 実装方針 | 具体的な実装方針。既存資材があればそれをベースにする |
| `tasks.md` | 先頭のチェックリスト | 実装タスクの分解（delta specのチェック項目はテンプレートのまま残す） |

情報が不足している箇所は推測で埋めず、`proposal.md`の「影響範囲」または `design.md` に
質問として明記する（承認時のレビュー観点になる）。

**A-3.** `docs/tasks/todo.md` に以下の形式で1行追記する（未着手・承認待ちの残タスクとして
反映するため。既存の運用メモの区分に合わせる場所が無ければ新設してよい）。

```
- [ ] <change-name> — 提案中・承認待ち → docs/changes/<version>-<change-name>-<日付>/proposal.md
```

過去に提案が `todo.md` に一度も反映されず日次棚卸しから漏れた事例があるため
（`directry-rules.md` 4.3）、この追記は省略しない。

**A-4.** `docs/specs/`（大本spec）はこの時点では変更しない（Spec-First: 実装フェーズで直接更新し、
差分は `specs/` にunified diffで残す。`directry-rules.md` 4.2）。

### B. ops系の場合

**B-1.** 依頼に対応する `order-yyyymmdd/` が無ければ、
`~/.claude/commands/init-ops-work.md` のワークフロー（対象ディレクトリ決定・
依頼ディレクトリ決定・重複チェック・テンプレートコピー・todo.md追記）に従って作成する。
既にあれば流用する。

**B-2.** `order.md` に依頼内容（何を・いつまでに・誰から）を書く（Notion等の外部ソースが無い、
その場で受けた依頼として書き起こす）。

**B-3.** 手順2の調査結果と依頼内容をもとに `plan.md` の以下の見出しを埋める。**見出しは変更しない。**

| 見出し | 書く内容 |
|---|---|
| 依頼概要 | order.mdの要約。何を・どの範囲で・なぜ |
| 調査結果 | 手順2の結果。参照したファイルパスを明記する |
| 対応方針 | 実装方針。既存資材があればそれをベースにする |
| 対象データ | 対象件数・データソース・整合性の確認結果 |
| リスク・確認事項 | 不可逆操作の有無、情報が不足している点を質問として残す |
| 承認状況 | テンプレートのチェックボックスをそのまま残す |

情報が足りない箇所は推測で埋めない。「リスク・確認事項」に質問として書き出す。

業務ルール（履歴レコードの備考欄への記録方式など）が
`~/.claude/local/ops-work/RULES.md` にあれば読んで従う。無ければ黙って続行する。

**B-4.** `todo.md`（サブプロジェクト直下）への追記は `/init-ops-work` の手順内で行われる前提。
未追記なら本手順で追記する。

## today-todoバッチモードの最終レビュー（敵対的検証）

バッチモードで全サブエージェントの報告（0-4）が揃ったら、`todo-propose-checker`エージェント
（`Write`・`Edit`を持たない専任の検証エージェント。判定のみ可能で修正はできない。定義:
`~/.claude/agents/todo-propose-checker.md`）を**新規コンテキストで**起動し、各サブエージェントの
報告を鵜呑みにせず成果物をゼロから再検証させる。0-2でサブエージェントを並列起動した張本人である
メインセッションが自分で検証すると、合格させたい方向に評価が甘くなりやすいため、判定は起票と
別コンテキストのCheckerに分離する。

`todo-propose-checker`に渡すもの:

- 0-4の全サブエージェント報告（項目内容・分類・作成/更新ファイルパス・調査結果の要点）
- 入力元の`todo-YYYY-MM-DD.md`へのパス

`todo-propose-checker`は少なくとも以下を自分で確認する（詳細な検証観点は`todo-propose-checker`
定義側に持たせ、本コマンドでは重複させない）:

- 「新規提案が必要」の起票内容に、手順2の調査結果として書かれたファイルパス・コマンドが
  実在し、記述と一致するか
- 「対象外」判定が0-3の基準表に照らして妥当か（恣意的な回避でないか）
- 既存ディレクトリ流用の原則（A-1/B-1）を破って重複作成していないか
- A-3（dev系）のtodo.md追記が実際に行われているか
- proposal.md/design.md/order.md/plan.mdの既存見出しを変更・削除していないか

`todo-propose-checker`が「要修正」と判定した項目は、指摘内容を添えて該当サブプロジェクトの
サブエージェントに差し戻し、再起票させたうえで再度`todo-propose-checker`にかける（合格するまで
0-2↔本節を繰り返す。ただし再起動するのは「要修正」となった特定のサブプロジェクトのみで、他の
サブプロジェクトの結果は巻き込まない。2周しても解消しない場合はループを打ち切り、ユーザーに
判断を仰ぐ）。

メインセッションは`todo-propose-checker`の判定もそのまま鵜呑みにせず、疑わしい点があれば自分でも
成果物を読み直して裏取りする。虚偽・過剰判定・雑な起票が見つかれば、ユーザーへの報告で明示的に
指摘する（黙って握り潰さない）。この検証を終えてから「## 3. 完了報告と停止」の内容を
サブプロジェクトごとに集約して報告する。

## 3. 完了報告と停止

（バッチモードでは、上記「today-todoバッチモードの最終レビュー」を経たうえでサブプロジェクトごとに
以下を集約する。）

以下を報告し、**ここで停止する。承認前提で `src/`・実装コードには着手しない。**

- 作成・更新したファイルのパス（`proposal.md`/`design.md`/`tasks.md` または `order.md`/`plan.md`、
  `todo.md` への追記）
- 手順2の調査結果の要点
- 「リスク・確認事項」または質問として残した項目（あれば箇条書きで再掲）
- 承認後は改めて実装を依頼してもらう旨（本コマンドは実装フェーズを持たない）

### 3-0. 作業ログへの追記（両モード共通・必須）

`~/projects/today-todo/work-log-YYYY-MM-DD.md`（実行時のシステム日付）に
実行内容を1エントリ追記する。無ければ新規作成し、あれば末尾に追記する（既存エントリは変更しない）。
`todo-import` → `todo-propose` → `todo-execute` のワークフロー全体で「いつ何を実行したか」を
積み上げる実行履歴であり、成果物のスナップショットである `proposal-YYYY-MM-DD.md` とは別物
（`self-work/document-rules/document-rules.md` 参照）。

```markdown
## HH:MM — /todo-propose（単一対象 <対象パス> / バッチモード）
- 入力: {todo-YYYY-MM-DD.md の件数、または単一対象の依頼内容}
- 出力: {作成・更新したファイルパス。バッチモードは proposal-YYYY-MM-DD.md へのリンクのみで良い}
```

時刻は実行時刻（HH:MM、24時間表記）を使う。詳細を二重に書かず、リンクで参照させる。

### 3-1. まとめ版の書き出し（バッチモードのみ・必須）

バッチモードでは成果物が複数サブプロジェクトに散るため、**報告と同じ内容を1ファイルに残す**。
これを省略すると「どこに何が起票されたか」の入口が無くなる。

- 出力先: `~/projects/today-todo/proposal-YYYY-MM-DD.md`
  - 日付は入力に使った `todo-YYYY-MM-DD.md` と同じ値（＝実行時のシステム日付）。
  - ファイル名は固定。実装を含む横断実行計画（`plan-YYYY-MM-DD.md`、本コマンドの対象外）とは
    prefixが違うので、ファイル名だけで種別が判別できる。
  - 既存の場合は上書きせず、内容を追記・更新するか別トピック名にするかをユーザーに確認する。
- 記載する内容:
  1. 入力ファイルへのリンクと項目数、実行モード、「全件が承認待ちで停止」である旨
  2. サブプロジェクト×判定区分（新規起票／既存提案／決定待ち／物理作業）の集計表
  3. 新規起票分の一覧（件名と `proposal.md`/`plan.md` への絶対パスリンク）
  4. 最終レビュー（敵対的検証）で裏取りした発見事項。出典のファイルパス・行番号を必ず書く
  5. 留保・未確定事項（過剰生成の疑い、未検証の数値、暫定採番、意図的に直していない既存不整合など）
  6. 次アクション（承認する件を指定して実装を別途依頼する旨）
  7. **今日のゴールとマイルストーン（提案）**

  1〜6は上記の完了報告と同じで**新しい判断を足さない**。**7のみ例外**で、1〜6を踏まえて
  優先順位を提案する新しい判断を含む（2026-08-24追加、ユーザー指示。`self-work/document-rules/document-rules.md`
  に例外として明記）。

### 3-1a. 「今日のゴールとマイルストーン（提案）」の書き方（7、バッチモードのみ）

新規起票・決定待ちの項目全件を並列に扱わず、優先度の高いものに絞ってマイルストーン分解する
提案を書く。書式は以下の例に従う（過去の `today-todo/proposal-YYYY-MM-DD.md` に
「本日のゴールとマイルストーン」節としてこの形式で書かれた実例があれば参考にしてよいが、
日付が古いものはアーカイブ済みで消えている場合がある前提で、無くても本節の指示だけで書けるようにする）。

```markdown
### ゴール1: <ゴール名>（絞った理由を一言）

- **M1. <マイルストーン名>**（対象: <subproject>, モデル: sonnet, エフォート: medium）
  - 1-1 <サブステップ>
  - 1-2 <サブステップ>
- **M2. <マイルストーン名>**（対象: <subproject2>, モデル: haiku, エフォート: low）
  - 2-1 <サブステップ>

### 他（できたらやる・優先度低）

- <ゴールに含めなかった新規起票／決定待ち項目を列挙>
```

- ゴールを1〜3件程度に絞り、各ゴールに一言で絞った理由を書く。含めなかった項目は
  「他（できたらやる・優先度低）」として列挙する（切り捨てない、格下げして残す）。
- 各ゴールを `M1`・`M2`…のマイルストーンに分解し、マイルストーンごとにサブステップ
  （`1-1`・`1-2`…）を箇条書きにする。
- 各マイルストーンに、**対象サブプロジェクト**（`projects/`からの相対パス。1件のみ。複数
  サブプロジェクトにまたがる作業は、サブプロジェクト単位でマイルストーンを分ける）、
  提案する**使用モデル**（`haiku`/`sonnet`/`opus`）、**エフォート**（`low`/`medium`/`high`）を
  付記する。モデル/エフォートの判断基準は `model-routing` skill の判断軸
  （列挙・検索か判断・統合か、誤りが後工程で検出可能か）に従う。迷ったら下げない。
  対象サブプロジェクトを明記するのは、`/todo-execute`（承認されたマイルストーンを実装する
  コマンド）がここから対象・並列実行グループを機械的に読み取れるようにするため
  （`self-work/document-rules/document-rules.md` 参照）。
- **これは提案であり確定ではない**。実行順序・要否の最終判断、および実装着手（`/todo-execute`
  等）はユーザーが行う。本コマンドはこの提案を書いた時点でも停止する（実装フェーズを持たない
  という本コマンドの原則は7でも変わらない）。
- 書き出したら、**ファイル内のリンク先が実在するか全件チェックしてから報告する**（存在しないパスを
  書いた状態で完了報告しない）。
- 単一対象モード（`$ARGUMENTS` あり）では作らない。成果物が1ディレクトリに閉じており入口が不要なため。

## 注意事項

- 本コマンドはディレクトリの雛形作成を行わない（`/init-change`・`/init-ops-work` の責務）。
  雛形が無ければそれらのワークフローに従って先に作成する（手順A-1/B-1）。
- 承認は人間が行う。AIが自己判定して次工程（実装）に進まない。
- dev系・ops系いずれも、既存資材の調査（手順2）を省略しない。
- 案件固有の業務ルールは本コマンドに書かない。ops系の業務ルール参照先は
  `~/.claude/local/ops-work/RULES.md`（無ければ黙って続行）。
- **提案そのもの**は対象サブプロジェクト内（`docs/changes/`・`order-yyyymmdd/`）に閉じる。
  横断して置くのはバッチモードのまとめ版（`today-todo/proposal-YYYY-MM-DD.md`、手順3-1）だけで、
  これは起票先への入口であって提案の実体ではない。
  実装まで進めるコーディネーター実行計画（`today-todo/plan-YYYY-MM-DD.md`）は別物であり本コマンドの
  対象外（本コマンドは提案書作成で必ず停止するため）。
  3者の違いは `self-work/document-rules/document-rules.md` 参照。
