# /game-review — 試作のレビュー

引数: `$ARGUMENTS` = ゲームのディレクトリ（省略時はカレント）。

最初に game-dev skill の `SKILL.md`・`references/design.md`・`references/test-release.md` を読む。**このコマンドはゲームを変更しない。**

## 手順

1. `playlog.md` があれば読み、コンセプト・これまでの仮説・人の判定・判定待ちの行を把握する。無ければコードと会話から1文コンセプトを復元し、推測であると明示する。
2. `node measure.js game.js` を実行する。雛形を使っていないゲームは、ルール部分を画面なしで回せるか確かめ、回せなければ「ロジックが描画から分離されていない」を指摘の1つにして、計測できた範囲を明示する。
3. コンセプトの言葉を数えられる主張に直し（`references/design.md`）、使い捨てスクリプトで測る。
4. 次の観点で照合する。根拠は計測値かコードの該当箇所で示し、どちらも無いものは推測と書く。
   - 狙った展開がルールから生まれているか（手順3の結果）
   - 機械で分かる赤信号（`references/test-release.md` の表）
   - 難易度の上がり方に緩急があるか、やられた理由が見えるか
   - 調整値が1か所にあるか、固定刻みで更新しているか、乱数の種を指定できるか
   - 進め方: 判定待ちの仮説に変更を重ねていないか
5. 人の判定が1件も無ければ、それを最初に書く（工程2の通過条件が未確認）。

## 出力

```
結論: 1〜2文（最も重い問題と、工程を進めてよいか）
指摘（重い順）: 表 [# / 指摘 / 根拠の数字 / skillのどの基準か]
問題なかった点: 計測で確かめたものだけ
次の一手: 仮説を1つ（「〜を変えれば〜になるはず」）と、先に人に見てほしい点
```

機械の計測は人の遊び方と違う。数字は方針同士の比較と偏りの検出に使い、難しさの絶対値としては書かない。指摘が複数あっても、次の一手は1つに絞る。
