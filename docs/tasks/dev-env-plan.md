# 複数プロジェクトの作業環境の整理

複数プロジェクトを手元とクラウドの Claude Code で並行して進めるときの、認知負荷・並列作業の混線・環境の汚れ・認証情報の散らばりを減らす。
考え方は「作業の記録を1か所にして毎日まとめさせる」「タスクごとに隔離した環境で動かす」「隔離環境の中に認証情報を置かない」の3つ。

backlog.md の #6〜#10 に対応する。上から順に着手する。依存: #8 は #6・#7 の後、#9 は #6 の後、#10 は #9 の後。

## #6 用途別のクラウド環境に分ける

- 現状: 1つの個人用クラウド環境を用途の違う作業で使い回しており、許可ホストが用途をまたいで溜まっている。
- 手順:
  1. クラウドセッションで `get_environment` を呼び、現在の環境の許可ホスト・ネットワーク機密・セットアップスクリプトを確認する。
  2. 用途の分け方と、用途ごとに許可するホストを利用者と決める（AskUserQuestion。候補の例: dotfiles と skill の作業、調べもの、プロジェクトごとの開発）。用途ごとに、通るべきホストと確認用のコマンド（例: `curl -sI https://<host>`）を表にしてこのファイルに追記する。ネットワーク機密が要るホストは、認証が要るAPIを1回呼ぶ確認を表に入れる。
  3. 用途ごとに `create_environment`（scope: personal）で環境を作り、その用途に要るホストだけを許可する。
  4. 旧環境から用途外のホストを外すかは利用者が決める（外すと、その環境を使う既存の作業が通信できなくなる）。
- 注意: 環境の作成・変更は毎回承認カードが出る。ネットワーク機密は環境をまたいで移らないので、必要なものは新しい環境で `request_credential` から登録し直す。
- 完了条件: 新しく作った各環境の許可ホストが用途の分だけになり、その環境の新しいセッションで、手順2の表の確認コマンドがすべて通る。旧環境は手順4の判断どおりになっている（外すと決めたホストが消えている）。

### 用途別の環境（手順2の表）

確認コマンドは、その環境の新しいセッションで `curl -s -o /dev/null -w "%{http_code}" https://<host>/` を実行する。許可外の確認先として `example.com` が拒否されることも見る。パッケージ取得（npm・PyPI など）はどの環境でも許可している。

| 環境 | 対象リポジトリ | 許可するホスト |
|---|---|---|
| dotfiles・調べもの | dotfiles、claude-context-pii-guard-ui、tech-blog-lib | www.youtube.com、zenn.dev、speakerdeck.com |
| Overwatch系 | overwatch-blog-web、overwatch-tournament-web、overwatch-tournament-ops、overwatch-information-rag | overwatch.blizzard.com、overfast-api.tekrop.fr、d15f34w2p8l1cc.cloudfront.net、api.cloudflare.com |
| アプリ開発 | fishing-rpg-app、sugumemo-app、todo-timer-app、tech-stack-batte-app、autoeditbot、build-server | なし（用途不明だったストア系・huggingface は外した。必要になったら足す） |

確認結果（2026-11-25、各環境の新しいセッションで実行）: 許可したホストはすべて応答を返し（200・301・307・404 など。cloudfront の 403 は配信元の応答）、許可していない `example.com` はどの環境でも接続できなかった。アプリ開発では外した `play.google.com` も接続できなかった。

## #7 backlog の行IDを作業の起点・終点にする

- 狙い: 作業がローカル・クラウド・PRに散らばっても、backlog の1行から辿れるようにする。
- 手順:
  1. `.claude/CLAUDE.md` の追加ルールに次を足す: 作業を始めるときは対象の backlog.md の行（`#<連番>`）を特定する／PR本文に `backlog: <リポジトリ名>#<連番>` を書く／終えたら行を `[x]` にする。途中で止めるときは、todo-format の状態欄（例: `（レビュー待ち）`）を書き換える。
  2. 子セッションへの指示文にも同じルールを含める（既存の「子セッションに自律ルールを渡す」ルールに追記）。
  3. 行から関連PRへは、GitHub のPR検索で `"backlog: <リポジトリ名>#<連番>"` を探して辿る。backlog 行にはPRのURLを書かない（todo-format の1行書式を変えないため）。
  4. today-todo viewer の列の backlog 同期とチェックの書き戻し（`today-todo/viewer/docs/specs/viewer.md` の 1.14・1.15）が、この行IDの使い方と矛盾しないか確認する。矛盾したら viewer 側は変えず、ルールの書き方を viewer の仕様に合わせる。
- 注意: 共有ファイルなのでリポジトリ名などの固有名を例に書かない（`<placeholder>` にする）。
- 完了条件: ルールを入れた後に作ったPRについて、PRから元の backlog 行に、行からPR検索で関連PRに辿れる。

## #8 毎朝の状況まとめを作る（#6・#7 の後）

- 狙い: 全プロジェクトの「進行中・止まっている理由・次の一手」を1ページで見られるようにし、自分で覚えておく必要をなくす。
- 手順:
  1. #6 で作った環境のうち、状況まとめ用の環境（#6 の用途の表に無ければ、#6 の手順で1つ足す）に、対象のリポジトリを付ける（プロジェクトはほぼ全て GitHub にある）。
  2. 新しいセッションを毎回起こすスケジュール実行（`create_trigger` の `create_new_session_on_fire`）を作る。時刻は利用者に確認する（AskUserQuestion）。
  3. 各実行で読むもの: 各リポジトリの `docs/tasks/backlog.md` の未完了行、開いているPR、前日のセッション一覧（`list_sessions`）。
  4. 出力はプロジェクトごとに「進行中・止まっている理由・次の一手」を並べた1ページ。スケジュール実行を作る側のセッションで先にArtifactを作り、そのURLをスケジュール実行のプロンプトに書く。各実行は同じURLを更新する。
- 注意: 対象リポジトリの一覧はこのリポジトリに書かない（業務の固有名を含みうる）。一覧は着手時に利用者から受け取り、スケジュール実行のプロンプトに直接書く。
- 完了条件: 初回のスケジュール実行で更新されたページだけで、どのプロジェクトの何が止まっているかを答えられる。
- 完了後: 「1週間使って見なくなった項目を削る」見直しを、別の行として backlog に足す。

## #9 リポジトリごとにワンコマンドで立ち上がるようにする

- 狙い: タスクごとの隔離環境（クラウドのセッション、手元のコンテナ）で、毎回同じ手順で開発環境が立ち上がるようにする。git worktree はファイルを分けるがプロセスを分けないので、並列作業でポートやDBが衝突する。
- 対象: 着手時に対象リポジトリと優先順を利用者に確認する（固有名はこのリポジトリに書かない）。1つ目のリポジトリで手順を通してから、残りに広げる。
- 前提: 手元で devcontainer を動かすには Docker が要る。無ければ導入前に利用者の確認を取る。
- 手順（リポジトリごと）:
  1. 依存の導入・DBなどの起動・シードデータ投入を1コマンドにまとめる（例: `make setup`）。
  2. クラウド環境のセットアップスクリプトからそのコマンドを呼ぶ（#6 で作った、そのリポジトリの開発用の環境に登録する）。
  3. 手元用に devcontainer の定義を置き、同じコマンドを呼ぶ。
- 注意: セットアップスクリプトは環境に平文で保存されるので、秘密を書かない。
- 完了条件: 1つ目のリポジトリで、新しいクラウドセッションと手元のコンテナの両方で、そのコマンドだけで起動とテストが通る（テストが無いリポジトリは起動確認のコマンドが通る）。
- 完了後: 残りのリポジトリを、1リポジトリ1行で backlog に足す（固有名は書かず、着手時に利用者が対象を指定する形にする）。

## #10 手元の認証情報を1か所に集める

- 狙い: リポジトリ配下に散らばった `.env` やトークンをなくし、エージェントのコンテキストに秘密が載る経路を断つ。
- 手順:
  1. 手元のマシンで、#9 で1コマンド化したリポジトリにある平文の秘密ファイルの場所を一覧にする（中身は開かない）。#9 がまだ届いていないリポジトリは、#9 の追加行が終わってから同じ手順で行う。
  2. シークレット管理ツール（例: 1Password CLI の `op run`）に移し、実行時だけ環境変数として渡す。新しいツールの導入になるので、導入前に利用者の確認を取る。
  3. 手順1で見つかった秘密のうち、クラウドのセッションでも使うもので、#6 でまだ登録していないものを環境のネットワーク機密に登録する（セッション内に本物のキーが入らない）。
- 注意: 秘密ファイルを `cat` などで開かない。ログにも出さない。
- 完了条件: 対象のリポジトリ配下に平文の秘密ファイルが残っておらず、#9 で作った1コマンドで開発とテストが動く。
